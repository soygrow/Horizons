# 13 · 每日情报（/daily）落地方案

> 目标：用 0 元新增成本，每天产出一份 10–15 条、可核验、分模块的中文 AI 情报。
> 面向：想创业的人、想用 AI 赚钱的人、AI 从业者、只要一手资讯的人。
> 已落地：导航「每日情报」→ `/daily` 日报首页（`apps/site/src/pages/daily/index.astro`），首屏即最新一期。

## 1. 命名与定位

| 项 | 决定 |
| --- | --- |
| 导航名 | 每日情报（2 音节可扫读，比「资讯」更强调筛过、有判断） |
| 路由 | `/daily` |
| 一句话 | 每天 7:30，一份能直接用的 AI 情报 |
| 与榜单的关系 | 榜单回答「现在什么在涨」，情报回答「今天发生了什么」 |

不叫「日报」：日报暗示信息搬运；「情报」暗示筛选、核验、判断，和本站「可追溯」口径一致。

## 2. 模块：5 个固定 + 1 个观察区

模块数定 5 个，超过 6 个读者会跳读，少于 4 个覆盖不了四类受众。

| # | 模块 | 条数 | 回答的问题 | 主要服务 |
| --- | --- | --- | --- | --- |
| 01 | 今日头条 | 3–5 | 一天里最需要知道什么 | 只要一手资讯 |
| 02 | 模型与产品 | 3–5 | 能力边界变了没有 | 开发者 / 从业者 |
| 03 | 开源与工具 | 2–4 | 有没有能白嫖、能二次开发的 | 想低成本做出东西 |
| 04 | 商业与赚钱信号 | 2–3 | 成本线在哪、谁在赚钱 | 想创业 / 想变现 |
| 05 | 今天就能做 | 1–3 | 现在能动手试什么 | 全部 |
| — | 未证实观察区 | 不定期 | 有哪些早期传闻 | 想看早期信号 |

硬规则：**观察区内容永不进头条**，也不写成已发生的事实。

## 3. 数据源：只接免费的，并且只用允许的方式

| 源 | 接入方式 | 额度（免费） | 主要信号 |
| --- | --- | --- | --- |
| Hacker News | Algolia：按分数拉窗口内全部候选（1–2 次请求），本地做 AI 过滤 | 匿名可用，约 1 万次/小时 | 社区讨论、产品发布 |
| GitHub | 公开 Search API，每个 topic 两轮查询 | 匿名搜索 10 次/分钟；个人 PAT 5000 次/小时（不花钱） | Star 增量、活跃度、新项目 |
| 科技媒体 | RSS | 免费 | 已报道事件、公司动态 |
| Hugging Face | 公开 API（`sort=createdAt`） | 免费无需 key | 新模型、新数据集、下载/点赞变化 |
| X | **人工**检索官方账号与维护者 | 0 | 中文圈早期信号、预告 |

红线：
- 不买 X API，不爬需登录页面，不绕速率限制。
- 免费公开 ≠ 可无限自动采集；遵守各站 ToS 与 robots。
- 一个仓库每天只采样 1 次 Star，用于算增量，不做高频轮询。

## 4. 技术落地：复用现有仓库，不另起 Python 项目

原方案是 Python + SQLite + cron。本项目已经是 TS + Astro 静态站 + GitHub Actions，另起一套会带来两份去重逻辑和两套口径，反而更贵。改为：

```
content/
  digest/
    raw/2026-10-30.json        # 每天一份原始候选，进 git（唯一真源，可回溯）
    state/github-stars.json    # Star 采样历史，用于算跨日增量
    state/seen.json            # 跨天「见过」索引，用于首次发现时间与旧闻识别
scripts/fetch/daily/
  run.ts                       # 入口：pnpm fetch:daily（--dry / --only / --limit / --date）
  config.ts                    # 源、topic、阈值、关键词组
  http.ts                      # UA / 超时 / 有限重试
  normalize.ts                 # 统一结构、URL 规范化、AI 相关性闸门、源内归一化
  store.ts                     # 原子写入、Star 采样、seen 索引
  types.ts                     # RawItem / RawDigest / Digest 契约
  events.ts                    # 事件合并（链接 / 实体 / 版本 / 动作四重校验）
  score.ts                     # 证据分级 + 重要性 + 热度 + 模块分配
  compose.ts                   # 模板成稿（不调付费模型）
  build.ts                     # pnpm digest:daily
  sources/hackernews.ts
  sources/github.ts
  sources/rss.ts
apps/site/src/lib/digest.ts    # 构建期读取 content/digest/*.json
apps/site/src/pages/daily/
  index.astro                  # 日报首页：最新一期头条全文 + 其余模块 + 往期
  [date].astro                 # 单期日报页（全模块、来源与数据源健康度）
```

SQLite 只在本地调试时需要；线上与 CI 用 JSON 即可，避免引入运行时数据库。

### D1–D7 实测结果（2026-10-30）

| 指标 | 实测 |
| --- | --- |
| 候选条数 | 111（HN 19 / GitHub 86 / RSS 6） |
| 合并后事件 | 111（当日无可信重复对） |
| 成稿条数 | 15（头条 4 / 模型与产品 4 / 开源与工具 4 / 商业 1 / 可执行 2） |
| 证据 | 已核验 12，待核实 3 |
| 单轮耗时 | 采集约 53 秒 + 成稿 < 1 秒 |
| 去重 | 同日重复运行不重复入库；跨天用 seen 索引标记旧闻 |

六处必须记住的实现结论：

1. **HN 不能用关键词搜索当主力**。"AI model release" 这类多词查询在 30 小时窗口内只回 2 条；改为按 `points>25` 拉全量候选（83 条）再本地过滤，AI 相关 22 条，召回率差一个数量级。
2. **GitHub 不能只按累计 Star 排序**。否则永远被巨型老项目占满；改为「活跃榜（`pushed:>7d`，sort=updated）+ 新星榜（`created:>120d`，sort=stars）」两轮，在没有跨日采样时用 `平均每日得星 = stars / 存活天数` 兜底。
3. **标题合并不能用词集 Jaccard**。实测「同一事件的不同写法」得分 0.38，「不同事件」得分 0.40–0.44，指标完全失效。改用四重闸门：动作词冲突（发布 vs 定价）直接否、机构名冲突（DeepSeek vs Qwen）直接否、版本号冲突（V4.1 vs V5）直接否，最后才比内容词重合度（有实体锚 0.6 / 无锚 0.85）。宁可漏合并，错合并会直接毁掉头条可信度。
4. **"agent" 这类弱词必须做二次校验**。初版把 `Undercover ICE Agents` 的移民新闻当成 Agent 情报送进了头条。现在 `agent / inference / gpu / mcp / transformer` 属弱词，必须有强词或第二个弱词兜底才算 AI 相关。
5. **仓库内容在头条「降权」不够，必须完全排除**。首轮复盘发现 `Ebony-Vinyl/dsh-our-free-model`（个人仓库，88 分）仍挤进第 4 条头条——88 分减 8 仍高于其余新闻。现在头条池直接过滤掉 GitHub 来源，仓库只走开源/产品模块，两条轨道不互相挤占。
6. **`other` 类别不能靠「来源是 RSS」就进头条或模型模块**。首轮把律所客户案例 `How Ropes & Gray is developing AI…`（category=other）送进了头条，`模型与产品` 也被 `How Ropes & Gray…` 占过位。现在模型模块只收 `model_release / product_launch / ai_coding`，头条先取非 `other`、凑不满 3 条才允许 `other` 兜底。

7. **「为什么值得关注」必须按角度和类别分句**。初版所有头条共用一句模块文案，同一屏出现两次一模一样的话，模板感很重。现在先按标题判角度（research / pricing / policy / release / incident），判不出退回类别句（`WHY_BY_CATEGORY`），最后才是模块句。

复盘工具：`pnpm digest:daily --review` 会额外列出未采用条目里分数最高的 20 条并标注丢弃原因，用来核对漏报。

## 页面层规则

- `/daily` 首屏就是最新一期：刊头速览卡（本期头条 4 条）→ 头条全文 → 其余模块紧凑列表 → 往期。产品说明、证据分级、数据源与流程全部下移，不再挡在日报前面。
- 详情页 `/daily/[date]` 的每个条目带 `id`，首页的模块列表直接链到对应锚点（`scroll-mt-24` 避开吸顶导航）。
- 导航在 `lg` 以下原本整体隐藏，手机上找不到入口。现在补一条可横向滚动的频道条（`NavBar.astro`），宽度足够时仍用原导航。
- 页面不写死任何数字：期号、候选数、核验数、采用数、筛选漏斗全部来自 `content/digest/<date>.json`；没有日报时显示「第一期正在生成」，不放假数据。

## 5. 数据契约（单期 JSON）

下面是**成稿**契约（`content/digest/YYYY-MM-DD.json`，D6–D9 产出）。采集中间态在 `content/digest/raw/`，字段见 `scripts/fetch/daily/types.ts` 的 `RawItem`，两者的差别是：raw 只有「一条信息」，成稿才有「一个事件 + 证据 + 模块归属」。

```jsonc
{
  "date": "2026-11-03",
  "generatedAt": "2026-11-03T07:30:00+08:00",
  "stats": { "candidates": 187, "merged": 96, "verified": 34, "published": 12 },
  "modules": [
    {
      "key": "headline",            // headline | model | oss | business | action | rumor
      "items": [
        {
          "id": "evt_20261103_01",
          "title": "一句话事件标题",
          "summary": "100 字以内，只写材料能支持的事实",
          "why": "为什么值得关注",
          "category": "模型发布",
          "evidence": "verified",   // verified | pending | rumor
          "score": 88,              // 内部保留，前端只映射热度档位
          "heat": 4,                // 1–5，score / 20 向上取整
          "firstSeenAt": "2026-11-03T05:12:00+08:00",
          "sources": [
            { "type": "official", "label": "官方公告", "url": "https://…", "verified": true }
          ]
        }
      ]
    }
  ]
}
```

## 6. 评分与核验

重要性（0–100）：技术/产品影响 40 + 新颖性 25 + 中文用户相关性 20 + 证据完整性 15。

热度单独算，不叠加原始分数：HN 分数与评论数、Star 增量、独立来源数，各自在源内归一化后加权。
**只有一次采样不得写「正在升温」**，至少两次间隔明确的采样才算变化量。

已实现的候选排序（`normalize.sourceSignalScore` + `normalizeScores`）：
- 各源先算自己的强度，再在**源内做 min-max 归一化到 0–100**，跨源不直接比大小。
- HN：`points + comments × 1.5`。
- GitHub：`starDelta × 30 + log10(1 + starPerDay) × 120`；第一天没有 delta 时 `starDelta=0`，靠 `starPerDay`（累计 Star ÷ 存活天数）区分新项目与老项目。
- RSS：暂无互动信号，只提供事实与链接，排序交给后续重要性评分。

证据三态：
- `verified`：官方公告 / 原始仓库 / 官方文档 / 可复现数据。
- `pending`：只有媒体转述或社区讨论，必须写明缺哪一块。
- `rumor`：未发布、泄露、预告，只进观察区。

转载不算独立来源；独立来源数按原始发布者去重。

## 8. 质量闸门（发布前自动检查）

1. 每条 `sources` 至少 1 条可访问 URL，且不是聚合站转载。
2. `rumor` 条目不得出现在 `headline` 模块。
3. 单期条数 10–15；不足 10 条就照实发，**不凑数**。
4. 摘要中出现的数字必须能在 `sources` 里找到出处，否则删除。
5. 同一事件只出现一次（跨模块也不重复）。

## 9. 什么情况下才加成本

| 触发条件 | 处理顺序 |
| --- | --- |
| 连续 7 期有效事件 < 8 条 | 先加免费源和关键词，不加钱 |
| 人工审核连续 3 天 > 60 分钟 | 先用免费额度模型做摘要草稿，仍不买 API |
| 需要 X 全量搜索 | 才评估付费 X API |
| 需要真实流量/搜索量 | 才评估已有的 DataForSEO |
| 需要实时（小时级）更新 | 最后才考虑加机器与调度 |

判断标准写死：只有「免费手段已试过且仍不达标」才进入下一档，避免一上来就买 API 做成半成品。

## 10. 14 天后的验收指标

- 采集成功率：5 个源里至少 4 个连续 7 天无失败。
- 去重质量：同一事件重复上榜 ≤ 1 次/期。
- 有效事件比例：发布条目中人工判定「值得看」≥ 70%。
- 证据完整率：100% 条目有可追溯来源。
- 人工耗时：从首期 60 分钟降到 20 分钟以内。
- 漏报率：人工回看已知热点，漏报 ≤ 2 条/期。
