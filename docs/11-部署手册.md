# 部署手册（Cloudflare Workers）

**一句话：`git push origin main`，GitHub Actions 自动构建并部署。**

**本地看最新效果只用一条命令：`pnpm local` → http://localhost:4321**（见第九节）

```bash
git add -A && git commit -m "..." && git push     # 常规发布：自动部署
pnpm deploy --dry                                 # 本地预演，只构建不上传
pnpm deploy site                                  # 应急：本地上传前端（弱网下偏慢）
pnpm deploy api --migrate                         # 后端 + 先跑 D1 迁移
pnpm deploy web                                   # 只发旧 Next 站（回滚备胎，无域名路由）
```

---

## 一、真实机制（重要）

**常规发布走 GitHub Actions，工作流在 `.github/workflows/`：**

| 工作流 | 触发 | 做什么 |
|--------|------|--------|
| `deploy-site.yml` | push main 且 `content/**`、`apps/site/**`、`packages/shared/**`、`scripts/build/**` 或锁文件变化 | `pnpm data` → `astro build` → `wrangler deploy`（horizons-site） |
| `deploy-api.yml` | push main 且 `apps/api/**` 等变化 | 类型检查 → `wrangler deploy`（horizons-api） |

构建与上传都在 GitHub 的机器上完成，不经过本地网络；本地不再需要 `wrangler` 登录也能发布。

**需要的仓库 Secrets**（Settings → Secrets and variables → Actions）：

| 名称 | 值 |
|------|-----|
| `CLOUDFLARE_API_TOKEN` | Cloudflare API Token（权限见下一节） |
| `CLOUDFLARE_ACCOUNT_ID` | `ee14ebe99e88bedee9f429f7e0e61dd6` |

`CLOUDFLARE_API_TOKEN` 用 Cloudflare 模板「Edit Cloudflare Workers」创建即可，需包含：

- Account → Workers Scripts → Edit
- Account → Account Settings → Read
- Zone `horizons.tools` → Workers Routes → Edit（`wrangler.jsonc` 里绑了 routes）
- Account → D1 → Edit（采集流水线直连 D1 REST API 写候选池/报告，缺这条会 403 code 7403）
- Account → Workers R2 Storage → Edit（`wrangler.jsonc` 绑了 `r2_buckets`，缺这条部署会失败）

**本地部署仍可用**（`pnpm deploy`），保留给它：紧急回滚、本地预演、需要先跑 D1 迁移的 api 发布。所有本地操作收敛到 `scripts/deploy.sh`，不要手工散跑 `wrangler deploy`。

> 历史：2026-10-29 之前没有 CI，`git push` 不会上线；2026-10-30 起改用 GitHub Actions 自动部署。

### AI 工具榜的数据源（2026-11-16 起）

榜单唯一真源是 D1 的当前版本快照，`content/aitools.json` **不再入库**（见 `.gitignore`）：

| 环节 | 位置 |
|------|------|
| 工作区（候选 / 人工确认） | `board_items`：`kind=new` 是新收录，`kind=refresh` 是线上条目重采集，两者互不可见 |
| 快照（线上榜单） | `board_listed`（名次/卡片）+ `board_listed_details`（完整 tool 对象，含 `pageStructure`） |
| 生效指针 | `app_config['config.current_version']`（发布新版本后切换） |
| 构建输入 | `pnpm data` 先跑四个 `hydrate-*.ts`，优先读 R2 快照，没有才按指针从 D1 还原 |

由此带来三条约定：

1. 后台「发布」只写 D1，不再产生榜单文件的提交；要不要重建站点看发布报告的 `changed`
   （`publish-tools.ts --report`），不再看 `git diff`。
2. 构建机必须有 D1 读权限：CI 用 `CLOUDFLARE_API_TOKEN`，本地用 wrangler 登录态。
   两者都没有时，`hydrate-tools` 会沿用已有缓存文件并告警；连缓存都没有则直接失败。
3. 回滚榜单 = 把指针指回上一期版本再重建。D1 只保留最近 3 期快照，
   所以「后台随便改、随时回滚」这个自由度只覆盖最近三期。

## 二、拓扑（2026-10-29 起）

| 资源 | Worker 名 | 代码 | 入口 | 域名路由 |
|------|-----------|------|------|----------|
| 前端（唯一） | `horizons-site` | `apps/site`（Astro 静态站） | `apps/site/wrangler.jsonc`（`./dist` 静态资产） | `horizons.tools/*` |
| 后端 | `horizons-api` | `apps/api`（Hono） | `apps/api/wrangler.jsonc`（`src/index.ts`） | `horizons.tools/api/*` |
| 数据库 | D1 `horizons-db` | `apps/api/migrations` | — | — |

两者都在同一个 Cloudflare 账号下，`pnpm deploy` 会依次发布 `site` 与 `api`。

## 三、前置条件

1. **wrangler 已登录**（每个新机器只需一次）：
   ```bash
   pnpm --filter @horizons/site exec wrangler login
   ```
   凭据存在 `~/Library/Preferences/.wrangler/`。换机器/清缓存后会失效，表现为部署报 401 或 `Not logged in`。
2. **依赖已安装**：仓库根执行 `pnpm install`（`apps/site` 自 2026-10-29 起也由 pnpm 管理，不再有 `package-lock.json`）。
3. **数据文件都不入库**：`content/{aitools,trends,models,github}.json` 是构建缓存，
   构建前由 `scripts/admin/hydrate-tools.ts` / `hydrate-trends.ts` / `hydrate-models.ts` /
   `hydrate-github.ts` 还原，需要 `CLOUDFLARE_API_TOKEN` 或本机 wrangler 登录态。
4. **R2 快照（构建的常规路径）**：每次发布成功后，workflow 会执行
   `hydrate-*.ts --upload-snapshot`，把整榜导出到 R2 `horizons-archive/boards/<board>/<version>.json`。
   构建时 `hydrate-*.ts` 先读这个对象（0 rows read，几秒），读不到才回退 D1 逐条还原。
   所以正常构建不消耗 D1 读额度；只有在发布流程漏掉导出、或换了账号时才会走回退路径。
   `HORIZONS_SNAPSHOT=0` 可整体关闭快照，`--no-snapshot` 只关单次。
5. **详情已瘦身**：`board_listed_details.detail` 不含 github 的 `readme` 全文
   （占原始体积 74.8%，构建侧从不用它）。需要 readme 时去工作区 `board_item_details`
   或 R2 原始采集对象里取，不要指望发布快照。

## 四、标准发布流程

```bash
# 1. 提交代码（先让 git 干净，避免线上版本无法对应某个 commit）
git add -A && git commit -m "..." && git push origin main

# 2. 自检：只构建不上传
pnpm deploy --dry

# 3. 正式部署（生成 content/dist → Astro 构建 → wrangler 上传 → 线上验收）
pnpm deploy
```

脚本结束时会打印：

```
✓ / → 200
✓ /tools → 200
✓ /github → 200
✓ /trends → 200
✓ /deploy-check-should-not-exist → 自定义 404 页
✓ 部署完成，用时 120s
```

任一检查不通过会以退出码 1 失败，提示去看 `wrangler deployments list`。

`content/dist/**` 是 `content/*.json` 的派生产物（由 `scripts/build/artifacts.ts` 生成），不入库，`pnpm deploy site` 会自动重算。

## 五、验收线上是否真的更新了

状态码 200 只是必要条件，还要看内容：

```bash
# 首页导航是否为新版三频道（AI工具榜 / GitHub榜 / AI趋势词榜单）
curl -s https://horizons.tools | grep -o "GitHub榜"

# GitHub 榜收录条数（应为当期入榜数，如 500）
curl -s https://horizons.tools/github | grep -oE "共 [0-9]+ 个可开发项目"

# 自定义 404 页是否生效（应有页面内容，而非空响应体）
curl -s -o /dev/null -w '%{http_code}\n' https://horizons.tools/deploy-check-should-not-exist
```

> `*.workers.dev` 域名在部分网络（如本机 ISP）会被 reset，本机无法直接访问 `horizons-site.*.workers.dev`。验收请走主域，或用 `pnpm --filter @horizons/site exec wrangler dev` 本地核对。

## 六、回滚

**回滚到上一个成功版本**（分钟级，旧 Next 站已于 2026-11-06 删除，不再有跨站回滚路径）：

```bash
pnpm --filter @horizons/site exec wrangler deployments list
pnpm --filter @horizons/site exec wrangler rollback <version-id>
```

后端同理，把 `@horizons/site` 换成 `@horizons/api`。

## 七、数据库迁移

只在 `apps/api/migrations` 有新增时执行：

```bash
pnpm deploy api --migrate
```

### 后台管理（`/admin`）

只有站主本人能登录，账号密码都放在 Secret 里，站上没有注册或找回入口：

```bash
# 1. 生成密码哈希（交互输入，不回显；至少 12 位）
node apps/api/scripts/admin-password.mjs

# 2. 写入两个 Secret（值不要提交到仓库）
cd apps/api
pnpm exec wrangler secret put ADMIN_USERNAME
pnpm exec wrangler secret put ADMIN_PASSWORD_HASH

# 3. 首次上线要跑 0005_admin.sql（会话表 + 登录限流表）
pnpm deploy api --migrate
```

- **迭代次数不能用 210000**：Workers 的 WebCrypto 对 PBKDF2 有硬上限 100,000，超了线上直接抛 `NotSupportedError` 变 500（本地 miniflare 不报错，只会在部署后暴露）。脚本已固定 100,000，不要手工调大。
- 密码至少 16 位（迭代数受限，用密码长度补强度）。
- 本地开发写在 `apps/api/.dev.vars`（已被 `.gitignore` 忽略），格式同上。
- 入口：`https://horizons.tools/admin`，与站点同源调用 `/api/admin/*`。
- 会话 8 小时自动失效；同一 IP 15 分钟内失败 5 次锁定 15 分钟。
- 怀疑密码泄漏：换掉 `ADMIN_PASSWORD_HASH`（重新生成），并清会话表立刻踢掉所有已登录会话：
  `pnpm --filter @horizons/api exec wrangler d1 execute horizons-db --remote --command "DELETE FROM admin_sessions"`

#### 付费按钮点击统计（后台「付费记录」页签）

- 只统计定价页的 4 个下单按钮（月 / 年 × 自动续费 / 一次性），**点一次记一条，不代表成交**；成交看同一页签下面的付费记录。
- 按钮 key 是统计主键：白名单在 `apps/api/src/lib/paywall.ts`，前端上报在 `apps/site/src/lib/paywall-track.ts`，**两边必须一起改**；改 key 等于把历史数据切成两半。
- 口径：**只统计登录后的点击**。匿名点按钮会先跳 Google 登录，那一次不计入（前端看到 401 就不上报，服务端对无会话请求也直接丢弃）；表里 `user_id` 非空，人级归因就是「一个账号一个人」。
- 上报接口 `POST /api/track/paywall`：校验同源 `Origin`、要求已登录会话、只收白名单 key、同一账号 3 秒内重复点同一按钮只记一次、单日上限 200 次；任何异常都返回 204，绝不影响下单。
- 首次启用要跑 `0006_paywall_clicks.sql`（`pnpm deploy api --migrate`）。
- 怀疑被刷时清空重来：`pnpm --filter @horizons/api exec wrangler d1 execute horizons-db --remote --command "DELETE FROM paywall_clicks"`。

#### 数据字段健康度（后台「数据字段」页签）

- 数据来自 `scripts/build/field-health.mjs`：读 `content/dist/*` 与 `content/digest/*`，输出 `apps/site/public/data/field-health.json`（构建产物，已被 `.gitignore` 忽略）。
- 已接入 `pnpm --filter @horizons/site run data`，CI 每次部署都会重算，所以面板上的覆盖率就是当次部署的真实数据。
- 字段口径（来源 / 可能的问题）写在脚本顶部的 `FIELDS` 里，**改采集链路时要同步改这里**，否则面板会继续显示旧口径。
- 覆盖率为 0 的必填字段通常代表对应采集任务没跑成（例如 `g30` 整表为空 = Star 快照任务缺失）；标了「可缺省」的字段（如 `pricing`、`params`）缺失属常态。
- 页面上的「重新获取」只会重新读取最新快照（带缓存穿透），**不会重新采集原始数据**。真要重采：

```bash
pnpm fetch                    # 工具榜 / GitHub 榜：PH + GitHub + 流量/权重
pnpm models:collect           # 模型榜
pnpm trends:collect           # 趋势词
pnpm --filter @horizons/site run data   # 重算 content/dist 与 field-health 快照
git add -A && git commit -m "chore(data): refresh" && git push   # 触发部署
```

#### 趋势榜后台（后台「趋势榜」页签）

采集与发布都跑在 GitHub Actions，Worker 只负责触发和读仓库文件：

| 环节 | 落点 | 说明 |
|------|------|------|
| 拉取新词 | `fetch-trends.yml` | `run.ts --staging`，只写 `content/trends-staging.json`，线上榜单一个字都不动 |
| 审核 | `/api/admin/trends/staging*` | 拒绝会写进 `rejected`，下次采集直接跳过 |
| 发布 | `publish-trends.yml` → `scripts/admin/publish-trends.ts` | 合并进 `content/trends.json`，把位次变化写回 `lastPublish`，再 dispatch `deploy-site.yml` |

需要配置（`.dev.vars.example` 里有同名项）：

```bash
cd apps/api
# 只列名字、不显示值；两条都在就说明配好了
pnpm exec wrangler secret list | grep -E "GITHUB_TOKEN|GITHUB_REPO"
```

- `GITHUB_TOKEN`：fine-grained PAT，必须同时有 `Contents: Read and write` 与 `Actions: Read and write`（dispatch workflow 要后者），权限少一个就会在拉取时 403
- `GITHUB_REPO`：`owner/repo`，例如 `your-name/Horizons`
- 仓库 Secrets：`TRENDS_PROXY`（Google Trends 对 Azure 机房 IP 限流，不配大概率 429）、`DEEPSEEK_API_KEY`（复用现有）、`ADMIN_BOT_TOKEN`（选填；发布后触发构建用，不配则用 workflow 自带 token + `actions: write`）
- 迁移：`0009_trend_jobs.sql`（任务记录表）。漏跑时拉取仍会触发，只是后台看不到进度条，不会再误报失败

榜单上限 **1000 条代表词**（`MAX_BOARD_SIZE`，在 `packages/shared/src/trends-rank.ts`）：发布时按排位规则留前 1000，超出淘汰尾部，别名跟着代表词一起下架；后台「发布预览」会显示「超上限淘汰 N」，预览与发布共用同一份 `trimBoard`，不会出现预览 1100 条、实际写 1000 条。

## 八、常见坑

| 现象 | 原因 / 处理 |
|------|------------|
| push 之后线上没变 | 先看 Actions 是否被触发（paths 过滤）、是否因缺 Secrets 失败；也可在 Actions 页手动 `Run workflow` |
| Actions 报 `Authentication error [code: 10000]` | `CLOUDFLARE_API_TOKEN` 缺 Zone `horizons.tools` 的 Workers Routes 权限，或已过期 |
| 采集显示成功但后台「待发布」为空 | 候选池只写 D1，写入不完整时采集步骤会直接失败（不会再出现「文件里有、后台没有」）。日志里若见 `D1 HTTP 403`（code 7403），说明 `CLOUDFLARE_API_TOKEN` 缺 `Account → D1 → Edit`，补权限后重跑采集即可 |
| `astro build` 报 `Missing field tsconfigPaths on BindingViteResolvePluginConfig.resolveOptions` | astro 升到 6.5+/vite 8（rolldown）后与 `@tailwindcss/vite` 不兼容。已在 `apps/site/package.json` 固定 `astro@6.4.4`、根 `package.json` 加 `pnpm.overrides.vite=7.3.7`，勿随意升级 |
| `astro build` 报 `ERR_PACKAGE_PATH_NOT_EXPORTED: entities/escape` | `apps/site/node_modules` 与锁文件不一致（`parse5` 需要 `entities@^6`）。删掉 `apps/site/node_modules` 后根目录 `pnpm install` |
| 部署报 `Not logged in` / token 刷新失败 | 多为瞬时网络问题，先 `wrangler whoami` 重试；仍失败再 `wrangler login` |
| 部署成功但页面 404 | 检查 `apps/site/wrangler.jsonc` 的 `routes` 是否为 `horizons.tools/*`，以及访问的是否为主域名（无 www） |
| 自定义 404 不生效 | `not_found_handling` 必须是 `404-page`，且构建产物根目录要有 `404.html`（来自 `apps/site/src/pages/404.astro`） |
| 详情页文案缺失或类型报错 | 给 `apps/site/src/lib/i18n/zh.ts` 加了 key 却没补 `en.ts`；`DictPartial` 会强制英文键对齐 |

## 九、本地部署（看最新代码，固定流程）

**唯一入口：`scripts/serve-local.sh`（`pnpm local`）。不要再用 `astro dev` 或 `next start` 充当“本地部署”。**

```bash
pnpm local                 # 重算数据 → 全量重建 dist → 重启服务 → 自动验收（约 50s）
pnpm local -- --port 4330  # 换端口（默认固定 4321）
pnpm local:restart         # 代码没变，只重启服务（复用已有 dist）
pnpm local:stop            # 停掉本地服务
```

访问 http://localhost:4321 ，验收覆盖全部频道：`/ /tools /github /trends /daily /models /opportunity /opportunity/archive` + 自定义 404。频道清单在脚本的 `CHANNELS` 变量里，**新增频道时要同步加进去**，否则“只部署了一部分页面”不会被发现。

> 端口说明：根 `pnpm dev` 指向 `apps/site`（Astro 站），`pnpm dev:api` 起后端（8787）。另一个历史坑是多个 `astro build` 并发写同一个 `dist` 会互相覆盖，脚本已加构建锁 + 外部构建等待来规避。

固定下来的规则（每次结果一致）：

| 项 | 固定值 |
|----|--------|
| 端口 | `4321`（`--port` 可覆盖，但默认不变） |
| 产物 | `apps/site/dist`（`astro build` 自身会清空 outDir，已验证；不再手动 `rm -rf`，避免撞上环境的批量删除拦截） |
| 数据 | 先跑 `pnpm --filter @horizons/site run data`，保证 `content/dist` 与 `content/*.json` 一致 |
| 服务 | `scripts/local/static-server.mjs`，复刻 Cloudflare `drop-trailing-slash` 规则：`/tools` → `tools/index.html`，`/tools/` → 308 到 `/tools`，未命中 → `404.html`，全部 `no-store` |
| 完整性断言 | `index/tools/github/trends/daily/404.html` 必须存在，HTML 总数 ≥ 200，否则直接失败 |
| 日志 / pid | `.local/build.log`、`.local/server.log`、`.local/server.pid`（已入 `.gitignore`） |

排错顺序：

1. 构建失败 → 看 `.local/build.log` 末尾 60 行；
2. 服务起不来 → 看 `.local/server.log`，多为端口被占（脚本会自动 kill 占用 4321 的旧进程）；
3. 页面 200 但内容旧 → 说明你开的不是 4321，而是残留的 `astro dev`（4322/4323）或旧 Next 站（3000）；`lsof -nP -iTCP -sTCP:LISTEN | grep node` 核对后关掉。
