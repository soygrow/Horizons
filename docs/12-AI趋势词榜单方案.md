# AI 趋势词榜单：产品与数据落地方案

**路由：** `/trends`（列表）+ `/trends/[slug]`（详情）
**导航：** 「AI趋势词榜单」
**数据形态：** 静态预生成 `content/trends.json`（沿用现有项目无运行时数据库的架构）
**文档版本：** V1.0

---

## 一、定位与用户

| 优先级 | 用户 | 最需要的信息 |
| --- | --- | --- |
| P0 | 独立开发者 / AI 创业者 | 新需求是什么、现有产品解决得好不好、从哪切入 |
| P1 | SEO 从业者 / 内容站长 | 增长是否持续、搜索意图、竞争情况、是否现在建页面 |
| P2 | 产品经理 / 技术研究者 | 新模型、新框架、新应用场景 |

产品差异点：**不是「什么正在流行」，而是「什么正在升温、为什么升温、现在可以做什么」**。

用户路径：发现新词 → 验证趋势 → 理解需求 → 获得行动建议。因此列表页承载「发现 + 验证」，详情页承载「理解 + 行动」。

## 二、准入规则（宽口径发现、严格准入、分层展示）

### 2.1 关键词范围（7 个一级类别）

| 类别 key | 中文 | 说明 |
| --- | --- | --- |
| `model` | AI 模型与品牌 | 新模型、模型版本、AI 公司与产品品牌 |
| `tool` | AI 工具与应用 | 具体工具、插件、应用、在线服务 |
| `agent` | AI Agent 与工作流 | Agent、自动化、MCP、智能体应用 |
| `devtech` | AI 开发技术 | 推理框架、开源项目、部署、评测工具 |
| `usecase` | AI 使用场景 | 用户想用 AI 完成的具体任务 |
| `business` | AI 商业与行业动态 | 引发实际产品或开发需求的发布、API 变化 |
| `broadtech` | 广义科技趋势 | 芯片、算力、开发平台、机器人（**更严格准入**） |

### 2.2 三条准入条件

- **A 明确关联**：能识别出具体产品 / 模型 / 技术 / 场景 / 开发需求。规则初筛 + LLM 分类。
- **B 可核验搜索证据**：至少有 Google Trends 近期记录或可复核的历史热度变化。只有新闻热度 → 进「待验证池」，不上主榜。
- **C 去噪**：合并拼写/大小写/同产品变体；过滤无关事件、单点异常、无意义缩写与随机串。

补充：新词缺少历史数据 ≠ 无效，状态标记为 `new`（新词观察），积累后再升级，不强行评分。

### 2.3 分层展示（三区 + 一个观测态）

| 状态 key | 展示名 | 判定 |
| --- | --- | --- |
| `breaking` | 正在爆发 | 近期增长显著、高于历史基线，且多时点证据排除单点噪声 |
| `gaining` | 持续增长 | 多个时间点持续升温，增长更稳定 |
| `new` | 新词观察 | 最近发现、历史不足、但与 AI 产品/场景明确关联 |
| `cooling` | 热度回落 | 当前热度低于爆发峰值并接近基线 |

## 四、数据字典（字段 → 来源 → 计算 → 验证）

| 字段 | 层级 | 来源 | 获取/计算 | 验证方式 |
| --- | --- | --- | --- | --- |
| `keyword` | 原始 | Trends Trending now / Rising / 产品发布 | 采集候选词，保留原始查询 | 可回溯原始链接 |
| `normalizedName` | 派生 | 官方产品页 | 规则标准化 + 实体识别 | 官方页面比对 |
| `category` | 派生 | 关键词 + 官方介绍 | 规则初筛 + LLM 分类 | 人工抽检 |
| `region` | 原始 | Trends | 记录 geo 代码 | 与采集参数一致 |
| `firstSeenAt` | 原始 | 自有库 | 首次采集成功即写入，不覆盖 | 库内最早记录 |
| `lastSeenAt` / `updatedAt` | 原始 | 采集记录 | 最近成功采集时间 | 采集日志 |
| `series` | 原始 | Trends Explore 历史兴趣 | 0–100 归一化序列 + 步长 | 与 Explore 截图/导出核对 |
| `baseline` | 计算 | `series` | 采样窗口内除最近 7 点外的均值 | 可复算 |
| `growth7` / `growth30` | 计算 | `series` | (近期均值 − 基线) / 基线 | 可复算；基线为 0 → 不可计算 |
| `peak` | 计算 | `series` | 序列最大值 | 可复算 |
| `persistence` | 计算 | `series` | 近 14 点中高于基线的点数占比 | 可复算 |
| `trendParts` | 计算+AI | 上述指标 + 采样质量 | 5 项归一 0–100，权重 30/25/20/15/10 | 分数构成可展开 |
| `confidence` | 规则 | 采样点数、基线稳定性、持续性、跨源一致性 | 证据等级：高/中/低 | 不依赖单一指标 |
| `opportunities` | AI | 意图 + 现有产品 + 用户讨论 | 生成 3–5 条，必须挂证据 | 每条须有依据，可人工复核 |
| `oppParts` | AI+规则 | 需求/缺口/SEO/可行性/时机 | 5 项 0–100，权重 30/25/20/15/10 | 同机会分析 |
| `evidence` | 原始+AI | 官方公告、新闻、仓库、社区 | 事件时间与趋势拐点关联 | 标注结论类型 + 发布日期 |
| `sources` | 原始 | Trends / 官方 / 社区 / 搜索 | 保存原始 URL 与类型 | 链接可访问 |

**关键口径纪律**

1. Google Trends 是**归一化相对热度**，不是搜索次数；页面禁止输出「月搜索量」推算。
2. 低基线放大增长率：基线过低或采样点不足时，`growth` 显示「—」，分数可标注「数据不足」。
3. 事件同天 ≠ 因果：详情页统一用「已验证事实 / 合理推断 / 待验证假设」三档标注。
4. 没有真实搜索量来源时，只展示相对热度、增长势头与趋势等级。

## 五、评分设计（两个独立分）

### 5.1 趋势强度分 Trend Score

`T = 0.30 × 增长幅度 + 0.25 × 持续性 + 0.20 × 爆发强度 + 0.15 × 新颖度 + 0.10 × 数据可靠性`

### 5.2 机会潜力分 Opportunity Score

`O = 0.30 × 用户需求证据 + 0.25 × 可切入空间 + 0.20 × 搜索与内容机会 + 0.15 × 独立开发可行性 + 0.10 × 趋势时机`

两分不混用：高趋势分不等于好机会（竞争可能已饱和），低热度新词也可能更适合独立开发者切入。数据不足时展示「数据不足，暂不评分」。

系统建议（规则推导，可解释）：

| 条件 | 建议 |
| --- | --- |
| T ≥ 70 且 O ≥ 65 | 值得研究，先验证需求 |
| T ≥ 70 且 O < 50 | 热度高但切入拥挤，建议只做内容 |
| T ≥ 50 | 可观察，等待更多证据 |
| 其他 | 暂不投入 |

### 5.3 综合得分与名次

`S = 0.6 × T + 0.4 × O`（两者均为 0–100，故 S 也是 0–100）

- 榜单按 S 从高到低排序，S 最高者为第 1 名；列表 `#` 列展示全站名次。
- 同分排序：先比 T，再比近 7 天增长，最后按 slug 稳定排序，保证构建结果可复现。
- 名次是**全站名次**，筛选、搜索、切换排序都不改变 `#` 编号，避免用户误以为筛选后名次变了。
- 采样点 < 14 的词不入名次表，`#` 显示「—」，永远排在已评分词之后。
- 趋势权重高于机会，因为榜单首先回答「什么正在升温」，机会是二级判断；权重需用历史表现回测校准。

### 6.2 列表页交互

1. 默认视图：单一排行榜，按综合得分 S 降序，每页 50 条，名次贯通全站。
2. 筛选（`cat` / `status` / `conf`）与搜索（`q`）只缩小结果集，不重算名次。
3. 排序：综合得分（默认）/ 趋势强度 / 机会潜力 / 近 7 天增长 / 最新发现；切换排序不改变 `#` 名次。
4. 规模：按 1000–2000 个关键词设计，列表只渲染当前页 50 行，筛选与搜索在服务端完成。
5. 详情页 `generateStaticParams` 会为每个词预渲染一页，词量到 2000 时构建页数同步上升（属预期成本）。

### 6.3 数据状态

`content/trends.json` 的 `mode` 字段只用于内部切换，不在前端展示。页面不声明数据来源状态，也不展示 seed 提示。

## 七、MVP 范围

**必须完成（本次已实现）**

- 七类关键词准入与三区/回落态分层展示；
- 综合得分排名 + `#` 名次列（全站名次，筛选不重排）；
- 1000–2000 词规模的列表（单页 50 行 + 服务端筛选/搜索）；
- 关键词、类别、状态、增长、可信度、原因、机会、更新时间 8 字段；
- 30 天热度序列 + 基线/峰值/持续性计算；
- 趋势强度分与机会潜力分（可展开构成）；
- 详情页 5 个区块（证据 / 事件 / 意图 / 机会 / 行动），每条附来源与结论类型；
- 每条建议标注依据与不确定性。

**第一版暂缓**

- 用户账户与订阅体系；
- 多国家/多语言同时覆盖；
- 每个词都生成完整 AI 报告；
- 实时搜索量估算；
- 历史不足仍强制排名。

**上线后观察**

1. 高分词 7/30 天后是否仍有热度；
2. 用户是否点击详情、查看证据与机会建议；
3. 高机会词能否产出可执行的内容选题或产品假设。

## 八、采集链路（已实现，全免费来源）

链路：`候选词发现 → 准入过滤 → Trends 兴趣曲线 → HN / GitHub 证据 → DeepSeek 单次富化 → 落库`

| 层 | 实现 | 数据源 | 成本 |
| --- | --- | --- | --- |
| 发现 | `trends/discovery.ts` | Trends Trending RSS（多地区）、工具库 `content/aitools.json`、种子池 `content/trends-seeds.txt`、GitHub 新建高星仓库、Product Hunt（可选） | 免费 |
| 准入 | `discovery.matchKeyword` | 可用性 + AI 相关性正则；工具库/种子仅做可用性校验 | 免费 |
| 验证 | `trends/sources/google-trends.ts` | Trends Explore 内部接口（等价 pytrends）：90 天日粒度，落库取最近 30 点 | 免费但有限流 |
| 证据 | `discovery.collectEvidence` | HN Algolia + GitHub Search | 免费 |
| 富化 | `trends/enrich.ts` | DeepSeek 单次调用产出分类/意图/机会/行动/机会分五维 | 按 token 计费，仅对入库词调用 |
| 评分 | `trends/score.ts` | 序列确定性推导趋势五维 + 阶段 + 可信度，可离线重算 | 免费 |

### 8.1 命令

```bash
pnpm trends:dry --limit 30      # 只看本轮排队（不联网、不调 LLM、不写文件）
pnpm trends:collect --limit 80  # 采集/刷新 80 个词，写入 content/trends.json
pnpm trends:rescore             # 不联网，按最新口径重算全库分数
pnpm trends:collect --with-ph --limit 40   # 额外启用 Product Hunt 发现
```

参数：`--limit` 本次联网验证上限；`--new-ratio` 新词占比（默认 0.4，其余用于刷新旧词）；`--refresh-after` 同一词最短重采间隔天数（默认 3）；`--geo` 主地区。

环境变量见 `.env.example`：`TRENDS_DAILY_BUDGET`、`TRENDS_REFRESH_DAYS`、`TRENDS_GEO`、`TRENDS_RSS_GEOS`、`GITHUB_TOKEN`（可选，提配额）。

### 8.2 频率与规模的关系

采集频率由 `--limit` 单点控制，榜单数量不受限制：

- 词池来自工具库 + 种子 + RSS + GitHub，天然可以长到 1000–2000 个；
- 每轮只验证 `--limit` 个词（建议 80–150），新词与陈旧词按 4:6 混合，避免每次全量重抓；
- 429 连续 3 次自动熔断，已采集结果每 10 个词增量落盘，不会因限流丢数据；
- 同一词两次采集之间至少隔 `TRENDS_REFRESH_DAYS` 天，曲线结论不会被高频重抓扰动。

按 1000–2000 词、每天 120 词计算，全库约 8–17 天轮转一遍；页面显示的是「各词最近一次成功采集」的结果。

### 8.3 已知限制

- `trends.google.com` 与 `api.deepseek.com` 需要能直连（或系统级代理）；脚本不内置 HTTP 代理支持，RSS 不可达时会自动跳过并继续跑 GitHub / 工具库来源。
- Google Trends 无官方 API，429 是常态，脚本按退避 + 熔断处理，不做重试风暴。
- 「为什么升温」的解释必须保留证据链接、证据日期、支撑内容与结论类型，不得把模型生成直接当事实（`claimType` 强约束在 prompt 与校验里）。
