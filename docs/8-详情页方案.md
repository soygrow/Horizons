# Horizon.tools 详情页实施补充：数据来源、字段映射与计算规则

在上一版详情页方案的基础上，我建议再补上一层真正可以交给开发人员执行的规范：每一个展示字段都要明确来源接口、原始字段、计算规则、数据库存储方式和前端展示条件。

下面以 DataForSEO 官方 API 文档为依据，把这些细节逐一落实。先明确一个关键原则：

- API 原始字段：由 DataForSEO 或官网直接提供。
- 派生指标：由 Horizon.tools 根据原始数据计算。
- 分析结论：根据指标和证据生成，需要保留引用依据。
- 未知数据：没有可靠来源时不展示，不用估算值冒充事实。

以下是第一版最值得接入的接口。链接均指向 DataForSEO 官方文档。

## 二、统一数据规范：先解决地区、时间和口径问题

所有数据都应该明确其统计条件，否则同一产品的两个数字可能根本无法比较。

### 2.1 必须统一的字段

| 字段                  | 推荐类型               | 用途            |
| ------------------- | ------------------ | ------------- |
| `product_id`        | UUID / BIGINT      | 关联产品          |
| `target_domain`     | VARCHAR            | 实际查询的域名       |
| `search_engine`     | VARCHAR            | Google、Bing 等 |
| `location_code`     | INTEGER            | 搜索地区          |
| `language_code`     | VARCHAR            | 搜索语言          |
| `period_start`      | DATE / NULL        | 统计开始日期        |
| `period_end`        | DATE / NULL        | 统计结束日期        |
| `collected_at`      | TIMESTAMPTZ        | 本平台采集时间       |
| `source_updated_at` | TIMESTAMPTZ / NULL | 数据源更新时间       |
| `source_endpoint`   | VARCHAR            | 实际调用的接口       |
| `raw_response_id`   | UUID / BIGINT      | 原始响应记录 ID     |
| `data_status`       | VARCHAR            | 正常、缺失、过期、失败等  |

`period_start` 和 `period_end` 应根据具体接口语义填写。如果接口返回的是某一时点的快照，而不是明确的统计区间，就不要自行假设它代表整月数据。

### 2.2 产品域名如何规范化

建议保存两个字段：

- `domain_original`：官网原始地址，例如 `https://www.example.com/`
- `domain_normalized`：规范化后的查询域名，例如 `example.com`

规范化时去除协议、常规的 `www` 前缀和路径，统一大小写；但不要随意把不同子域名合并。对于 `app.example.com` 和 `example.com`，应根据研究对象明确查询范围。

### 2.3 缺失值和异常值处理

| 情况          | 数据库处理     | 前端展示            |
| ----------- | --------- | --------------- |
| API 明确返回 0  | 保存 `0`    | 显示 0            |
| API 没有返回该字段 | 保存 `NULL` | 不展示该指标或显示“暂无数据” |
| 请求失败但存在旧数据  | 保留旧快照     | 显示旧值和更新时间       |
| 地区或语言不同     | 保存为不同数据记录 | 不直接混合比较         |
| 数据已超过设定新鲜度  | 保留原值并标记过期 | 显示“数据可能已过期”     |
| 字段含义尚未确认    | 暂不用于计算    | 不展示为正式指标        |

这套规范应当在接入第一个 API 时就落实，而不是等到前端出现数据矛盾后再补救。

# 三、模块 01：产品表现——API 字段与展示规则

## 3.1 主要数据来源


该接口最多可以查询 1000 个域名、子域名或网页，适合先批量建立产品基础数据。

[image](https://www.google.com/s2/favicons?domain=https://docs.dataforseo.com\&sz=32)

DataForSEO API v.3



### 3.2 字段映射

| 页面字段     | 推荐数据库字段         | API 原始字段                | 处理方式          |
| -------- | --------------- | ----------------------- | ------------- |
| 自然搜索流量估算 | `organic_etv`   | `metrics.organic.etv`   | 原样保存          |
| 自然搜索结果计数 | `organic_count` | `metrics.organic.count` | 原样保存，注明接口统计口径 |
| 付费搜索流量估算 | `paid_etv`      | `metrics.paid.etv`      | 原样保存          |
| 付费搜索结果计数 | `paid_count`    | `metrics.paid.count`    | 原样保存          |
| 采集时间     | `collected_at`  | 自有系统时间                  | 记录本次采集时间      |

特别注意：`organic_count` 不应直接标成“所有独立排名关键词总数”。Bulk Traffic Estimation 中的 `count` 描述的是相应搜索结果类别的计数。若页面要展示明确的排名关键词数量，建议以 Ranked Keywords 等排名明细接口及其统计口径为依据。

### 3.3 页面需要计算的指标

A. 自然与付费搜索估算合计

只有在确认两个 ETV 的统计范围和口径可相加时，才可以计算：

\\[ \text{搜索流量估算合计} = \text{organic\\\_etv}+\text{paid\\\_etv} \\]

建议命名为 `search_etv_total`，展示名称为“搜索流量估算合计”，不能命名为“月访问量”。

B. 自然搜索占比

\\[ \text{自然搜索估算占比}= \frac{\text{organic\\\_etv}} {\text{organic\\\_etv}+\text{paid\\\_etv}}\times100\\% \\]

计算条件：两个值都有效，且合计大于 0。

展示时必须写成“自然搜索估算占比”，不能写成“网站流量来源占比”，因为它不涵盖社交、直接访问、邮件等渠道。

C. 自然排名关键词数量

通过 Ranked Keywords 接口获取排名关键词明细后，按统一条件去重计数：

```
SELECT COUNT(DISTINCT keyword)
FROM product_keywords
WHERE product_id = :product_id
  AND location_code = :location_code
  AND language_code = :language_code
  AND snapshot_id = :snapshot_id;
```

这里的统计结果代表本次采集、指定地区和语言、所取结果范围内的去重关键词数。若只取前 1000 条，必须注明是“采集到的关键词数”，不能声称是全站所有排名关键词总量。

### 3.4 右侧分析如何生成

建议规则化生成第一版分析：

- 自然搜索 ETV 较高：描述为“自然搜索可见度较高”，并与同类产品比较后再下判断。
- 排名关键词多、前十关键词少：描述为“关键词覆盖较广，但高排名关键词占比有限”。
- 自然和付费搜索 ETV 都较高：描述为“搜索渠道同时存在自然与付费搜索信号”，不能推断其实际获客比例。
- 只有单一时间点：只分析当前表现，不生成增长结论。

同类产品比较必须使用相同地区、语言、搜索引擎、域名层级及相近的数据更新时间。

# 四、模块 02：增长趋势——历史字段与计算方法

## 4.1 数据来源

使用 [Historical Rank Overview](https://docs.dataforseo.com/v3/dataforseo_labs-google-historical_rank_overview-live/?utm_source=chatgpt.com)。

该接口支持指定历史日期范围，并提供 `date_from`、`date_to` 等参数。官方文档指出可查询的历史数据起始时间为 2020 年 10 月，但具体产品和日期是否有数据需要实际查询。

[image](https://www.google.com/s2/favicons?domain=https://docs.dataforseo.com\&sz=32)

DataForSEO API v.3



### 4.2 推荐存储字段

| 字段                       | 来源        | 用途       |
| ------------------------ | --------- | -------- |
| `period_date`            | 历史数据日期    | 趋势图横轴    |
| `organic_etv`            | 历史响应      | 自然搜索流量估算 |
| `paid_etv`               | 历史响应      | 付费搜索流量估算 |
| `organic_keywords_count` | 历史响应或排名数据 | 排名关键词数量  |
| `paid_keywords_count`    | 历史响应或排名数据 | 付费关键词数量  |
| `collected_at`           | 自有系统      | 本次实际查询时间 |
| `source_endpoint`        | 自有系统      | 记录数据接口   |

历史接口的实际响应结构需要按官方示例进行映射；不能预设所有字段都直接存在于历史响应中。如果历史接口未返回某项关键词统计，就使用相应的排名数据接口或自建快照计算，并标记数据来源。

### 4.3 变化率公式

例如比较 2026 年 9 月和 2026 年 10 月：

\\[ \text{月度变化率}= \frac{ETV\_{2026-10}-ETV\_{2026-09}} {ETV\_{2026-09}}\times100\\% \\]

计算前必须检查：

1. 两个时间点都有有效数据。
2. 地区、语言、搜索引擎和目标域名一致。
3. 指标口径相同。
4. 对比期大于 0。

如果对比期为 0，则不计算百分比，改为展示绝对变化量，并说明基期为零。

### 4.4 建议额外计算的趋势字段

| 字段                    | 计算方式                 |
| --------------------- | -------------------- |
| `change_absolute`     | 当前值 − 对比期值           |
| `change_pct`          | 根据变化率公式计算            |
| `trend_direction`     | 按设定阈值判断上升、下降、稳定或数据不足 |
| `positive_periods`    | 比较窗口内指标上升的有效时间段数量    |
| `negative_periods`    | 比较窗口内指标下降的有效时间段数量    |
| `data_coverage_ratio` | 有效数据点数量 ÷ 预期数据点数量    |
| `trend_confidence`    | 根据数据覆盖率、历史长度和口径一致性计算 |

其中，`trend_confidence` 是 Horizon.tools 自定义的数据质量指标，不是 DataForSEO 的官方评分。

### 4.5 建议采用的判断规则

- 只有两个时间点：可以计算变化，但不宜断言趋势持续。
- 连续多个时间点改善：可以描述为“连续改善信号”。
- ETV 增长但排名关键词下降：标记为“指标信号不一致”，继续调查。
- 缺失月份较多：降低结论确定性，必要时不输出趋势标签。

不要把一次短期暴涨直接称为“爆发式增长”，也不要将自然搜索估算增长解释成真实用户或收入增长。

### 5.3 关键词历史变化率

如果拿到同口径的历史搜索量：

\\[ \text{关键词需求变化率}= \frac{V_t-V\_{t-k}}{V\_{t-k}}\times100\\% \\]

这里 \\(V_t\\) 为当前月份搜索量，\\(V\_{t-k}\\) 为对比月份的搜索量。

推荐同时计算：

- `search_volume_current`
- `search_volume_previous`
- `search_volume_change_absolute`
- `search_volume_change_pct`
- `search_volume_trend`
- `search_volume_period`

对波动很大的关键词，可以使用连续 3 个月或 6 个月的平均值辅助判断，但需要保留原始月度数据，不能只展示平滑后的结果。

### 5.4 赛道需求总量不要直接相加

如果将一个赛道中的关键词搜索量相加，容易因为近义词、拼写变体和重叠搜索意图导致重复计数。

建议先按搜索意图聚类，再计算：

\\[ \text{关键词组需求指标} =\sum\_{i=1}^{n}\text{该组中去重后的关键词搜索量}\_i \\]

但这仍然只是关键词组的估算需求指标，不代表真实用户数或市场收入。若无法可靠去重，就只展示代表性关键词和单词趋势，不展示赛道总量。

# 六、模块 04：关键词机会评分——给出可复现的算法

关键词机会评分不是 DataForSEO 原始指标，而是 Horizon.tools 自己定义的分析模型。必须保存算法版本，并能解释每项分数从何而来。

## 6.1 评分输入字段

| 字段                         | 来源                  | 用途       |
| -------------------------- | ------------------- | -------- |
| `search_volume`            | Keyword Overview    | 需求规模     |
| `search_volume_change_pct` | 历史搜索量计算             | 需求变化     |
| `cpc`                      | Keyword Overview    | 商业意图线索   |
| `competition`              | Keyword Overview    | 广告竞争程度   |
| `rank_position`            | Ranked Keywords     | 当前产品排名   |
| `serp_competitors`         | SERP Competitors    | 搜索结果竞争格局 |
| `shared_keywords_count`    | Domain Intersection | 关键词重叠程度  |
| `score_version`            | 自有系统                | 算法版本     |

## 6.2 初版评分公式

建议将四个维度归一化到 0—100 分：

\\[ \begin{aligned} S\_{\text{opportunity}}={}&0.30S\_{\text{demand}}\\\ &+0.30S\_{\text{growth}}\\\ &+0.25S\_{\text{competition-gap}}\\\ &+0.15S\_{\text{commercial}} \end{aligned} \\]

其中：

- `demand`：搜索需求强度。
- `growth`：搜索需求增长。
- `competition-gap`：竞争空间。
- `commercial`：商业意图信号。

权重是第一版产品假设，不是行业标准，后续需要用真实样本验证。

### 归一化建议

搜索量通常呈现长尾分布，可以先使用对数转换，再映射到 0—100 分：

\\[ S\_{\text{demand}}= 100\times \frac{\log(1+V)-\log(1+V\_{\min})} {\log(1+V\_{\max})-\log(1+V\_{\min})} \\]

其中 \\(V\\) 为关键词搜索量，\\(V\_{\min}\\) 和 \\(V\_{\max}\\) 应来自固定的参考样本或预先定义的区间。

需要特别注意：如果每次都用当前查询结果的最小值和最大值归一化，评分可能随着样本变化而漂移。建议按市场、语言和算法版本固定参考区间，并保存这些区间。

### 缺失值规则

如果某个关键词没有历史搜索量，就不能把增长分记为 0。可以：

1. 不计算综合评分，展示“历史需求数据不足”；或
2. 仅对有效维度重新归一化权重，同时显示评分维度覆盖情况。

我更推荐第一版采用严格规则：关键维度缺失时不展示综合机会分，只展示已知的需求和竞争指标。 这样比生成一个看似精确的分数更可信。

### 6.3 广告竞争度不能直接作为 SEO 难度

`competition` 主要反映付费广告竞争，不能直接当作自然搜索难度。

如果需要构建 `competition_gap_score`，建议结合以下信号：

- SERP 中主要竞争域名的类型。
- 排名靠前结果的实际竞争情况。
- 竞品之间的关键词覆盖。
- 当前产品与竞品的排名差异。
- 关键词对应的具体使用场景。

在没有明确算法之前，先将这些数据作为证据展示，不必急于输出“SEO 难度 20/100”这样的数字。

### 7.3 竞品覆盖率的计算方式

如果有目标产品和竞品的完整、同范围关键词集合，可以计算：

\\[ \text{共同关键词比例} =\frac{|K_A\cap K_B|}{|K_A\cup K_B|}\times100\\% \\]

这里 \\(K_A\\) 和 \\(K_B\\) 分别是双方在相同地区、语言和查询范围下的关键词集合。

这个比例可以作为关键词集合相似度的参考，但不能直接代表产品功能相似度或市场份额。

还可以计算：

\\[ \text{目标产品独有关键词数}=|K_A-K_B| \\]

\\[ \text{竞品独有关键词数}=|K_B-K_A| \\]

如果数据只覆盖排名靠前的一部分关键词，页面必须注明“基于已采集关键词集合计算”，不能声称是完整覆盖率。

# 八、模块 06：创业机会报告——数据证据如何传递给 AI

这部分不需要继续购买大量新数据，而是将前面模块的结构化结果组合起来。

建议将 AI 输入固定为四部分：

1. 产品基本信息和官方功能。
2. SEO 与历史趋势数据。
3. 关键词需求和竞争证据。
4. 数据限制、缺失项和采集时间。

AI 输出使用固定的 JSON 结构，便于前端直接渲染。

```
{
  "opportunity_title": "具体的创业方向",
  "target_user": "明确的用户群体",
  "problem_hypothesis": "需要验证的用户问题",
  "product_concept": "产品构想",
  "differentiation": "差异化切入点",
  "mvp_features": [
    "核心功能一",
    "核心功能二"
  ],
  "evidence": [
    {
      "claim": "分析结论",
      "source_type": "keyword_metric",
      "source_id": "关联的数据库记录ID"
    }
  ],
  "risks": [
    "尚未验证的风险"
  ],
  "validation_plan": [
    "建议的验证步骤"
  ]
}
```

以上仅为输出结构示意，`source_id` 必须引用真实存在的记录，不允许模型自己生成不存在的数据 ID。

### 分析报告需要额外存储的字段

| 字段               | 作用           |
| ---------------- | ------------ |
| `report_id`      | 报告 ID        |
| `product_id`     | 对应产品         |
| `report_json`    | 完整分析结果       |
| `evidence_refs`  | 引用的证据记录      |
| `data_cutoff_at` | 本报告使用的数据截止时间 |
| `prompt_version` | 提示词版本        |
| `model_version`  | 模型版本         |
| `score_version`  | 评分算法版本       |
| `generated_at`   | 报告生成时间       |
| `report_status`  | 成功、失败或待复核    |

关键要求： AI 不负责计算基础指标，也不负责补齐缺失数据。程序先算出数据和评分，AI 再根据结构化数据生成解释。这样才能追踪每条分析结论的来源。

# 九、建议直接建立的数据库表

为了避免开发过程中反复调整数据结构，建议第一版至少建立以下 8 张核心表。产品官网的详细信息和报告可以单独存储，但 SEO 数据、关键词数据和分析证据必须有明确关联。

| 表名                    | 核心字段                                                                                                                            | 作用           |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| `products`            | `id`、`name`、`domain_normalized`、`category`、`description`、`pricing_url`                                                          | 产品基本信息       |
| `product_sources`     | `product_id`、`source_url`、`source_type`、`content_hash`、`fetched_at`                                                             | 官网信息来源及采集记录  |
| `api_jobs`            | `id`、`endpoint`、`request_params`、`status`、`cost`、`started_at`、`finished_at`                                                     | API 任务、费用与状态 |
| `api_raw_responses`   | `job_id`、`response_json`、`created_at`                                                                                           | 保存原始响应       |
| `seo_snapshots`       | `product_id`、`period_date`、`organic_etv`、`paid_etv`、`organic_count`、`paid_count`、`location_code`、`language_code`、`collected_at` | SEO 历史快照     |
| `keyword_metrics`     | `keyword`、`location_code`、`language_code`、`search_volume`、`cpc`、`competition`、`keyword_updated_at`                              | 关键词基础指标      |
| `product_keywords`    | `product_id`、`keyword_id`、`rank_position`、`ranked_url`、`snapshot_id`                                                            | 产品关键词及排名     |
| `opportunity_reports` | `product_id`、`report_json`、`evidence_refs`、`model_version`、`score_version`、`generated_at`                                       | 创业分析报告       |

另外，建议后续增加：

- `keyword_snapshots`：保存关键词历史搜索量。
- `backlink_snapshots`：保存反链历史快照。
- `product_competitors`：保存产品与竞争域名关系。
- `opportunity_scores`：保存各项评分、权重和算法版本。

不要把所有历史数据覆盖在一条产品记录上。产品表保存当前档案，快照表保存历史事实，报告表保存分析结果。

## 数据库约束建议

1. 对 `(product_id, location_code, language_code, collected_at, snapshot_type)` 等关键字段建立适当索引。
2. 对关键词设置统一规范化规则，并对地区、语言和关键词组合建立唯一约束。
3. 所有原始响应关联 `api_jobs`，以便追踪具体接口、参数和费用。
4. 评分结果必须关联 `score_version`，报告必须关联 `model_version`。
5. 对 `NULL`、零值、失败和过期数据分别处理，避免统计错误。

# 十、从 API 到页面的完整处理流程

建议将数据处理拆为六个阶段：

#### 01

采集任务

选择产品、地区、语言和接口，检查缓存及预算。

#### 02

原始响应归档

保存 API 请求参数、响应 JSON、费用、时间和任务状态。

#### 03

标准化入库

将 API 嵌套字段映射到统一的数据库字段，保留原始字段路径。

#### 04

计算指标

计算历史变化率、关键词集合、排名分布和可解释的机会评分。

#### 05

生成分析

把已验证的数据、计算结果和证据 ID 提交给 AI 生成分析报告。

#### 06

前端渲染

左侧显示数据，右侧显示结论，关键数字支持查看证据。

### 建议统一的内部 API

| 自建接口                                 | 返回内容           |
| ------------------------------------ | -------------- |
| `GET /api/tools/:slug/overview`      | 核心指标、数据状态、更新时间 |
| `GET /api/tools/:slug/history`       | 历史序列和变化率       |
| `GET /api/tools/:slug/keywords`      | 关键词列表和机会指标     |
| `GET /api/tools/:slug/market`        | 赛道关键词趋势和聚类     |
| `GET /api/tools/:slug/competitors`   | 竞品对比和关键词交集     |
| `GET /api/tools/:slug/opportunities` | 创业机会、证据链、验证计划  |

这些接口只读取自己的数据库，不能在用户每次打开页面时都实时调用 DataForSEO。这样可以控制成本、提高页面速度，也避免外部接口波动直接影响页面。

# 十一、第一版必须落实的计算规则

以下规则建议直接写进开发规格，不要留给开发人员临时决定。

| 指标        | 计算规则                  | 不允许的做法           |
| --------- | --------------------- | ---------------- |
| SEO 流量变化率 | 当前值与可比历史值计算           | 缺少基期时填 0%        |
| 关键词增长率    | 同口径、同范围的关键词集合对比       | 把不同查询范围直接比较      |
| 排名关键词数    | 统计明确采集范围内的去重关键词       | 把有限条结果当成全量       |
| 自然搜索估算占比  | 自然 ETV ÷ 自然与付费 ETV 合计 | 称为全站流量来源占比       |
| 关键词需求变化   | 同一关键词的可比历史搜索量         | 用不同地区数据计算趋势      |
| 关键词机会评分   | 固定规则、归一化、保存版本         | 把广告竞争度直接当 SEO 难度 |
| 竞品关键词重叠率  | 相同范围的关键词集合交集与并集       | 把重叠率当市场份额        |
| 赛道需求指标    | 统一关键词集合下的需求估算         | 直接当成市场规模或真实用户数   |
| 创业机会结论    | 数据事实与分析假设分开           | 把 AI 推断写成已经证实的事实 |

## 十二、开发时最容易踩的 5 个坑

1\. 把 ETV 当成真实网站访问量。 必须始终标注“自然搜索流量估算”或“付费搜索流量估算”。

2\. 把没有数据当成零。 没有返回关键词，不一定代表关键词不存在；也可能是数据覆盖、查询参数或返回数量限制导致。

3\. 将广告竞争度误认为自然搜索难度。 两者的含义不同，不能直接互换。

4\. 在没有历史数据时生成增长分析。 没有可比较时间点，就只能描述当前状态。

5\. 让 AI 自行补齐缺失指标。 AI 只能引用真实记录，不能凭空创造搜索量、收入、用户数量或竞品数据。

# 十三、推荐的实际开发顺序

我建议按以下顺序实施，不要先把全部 API 接入，再考虑页面如何呈现。

第一步：建立基础数据链路

先接入 Bulk Traffic Estimation，完成产品基础信息、原始响应存储、SEO 快照和顶部指标卡。

第二步：实现历史趋势

接入 Historical Rank Overview，验证真实返回字段，建立时间序列和变化率计算逻辑。

第三步：实现关键词分析

接入 Ranked Keywords 和 Keyword Overview，完成关键词表、搜索量趋势和初步机会筛选。

第四步：实现竞争分析

接入 SERP Competitors、Domain Intersection 和 Backlinks Summary，生成可追溯的竞品比较。

第五步：实现左右分析布局

每个章节左侧展示真实数据，右侧展示结构化分析，并为每条结论提供证据引用。

最后再强调一个实施重点：在正式开发前，先对每个准备使用的 DataForSEO 接口保存一份真实响应 JSON，并以这份响应验证字段映射。 官方文档能确定接口能力和字段含义，但具体返回结果仍可能因为查询参数、地区、数据覆盖和响应结构而不同。

只要把这一步做好，前面定义的页面字段、数据库结构和分析规则就能形成一条可复现的数据链路，而不是停留在概念设计阶段。
