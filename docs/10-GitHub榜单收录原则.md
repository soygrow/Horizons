# GitHub 榜收录原则（gh-rank-v1.3）

> 本文是**唯一口径**。每次重新拉取数据都按同一套判定执行，代码实现见
> `scripts/fetch/github-ranking-rules.ts`，执行脚本见 `scripts/fetch/rebuild-github.ts`。
> 换原则 = 升版本号（gh-rank-v2），并在本文"变更记录"里写清为什么改。

## 一句话原则

**一个项目能进榜，必须同时满足「AI 相关且可被二次开发」「真实活跃」「允许商业化」三个条件；总量不设上限，合格即收录，按综合得分排序。**

榜单不服务的对象：想看论文、数据集、教程的人。榜单只服务一种读者——**想用现成代码做出一个能收钱的产品的人**。

## 一、手工排除（不管数据多好看）

| 类型 | 为什么不要 | 判定 |
| --- | --- | --- |
| `awesome-*` / 清单 / 资源合集 | 没有可复用代码，无法做成产品 | 名称或简介命中 `awesome/curated list/...` |
| 教程 / 课程 / 书籍 / 笔记 / 路线图 | 是学习材料，不是底座 | 命中 `tutorial/course/book/learning/教程/入门/笔记` |
| 论文合集 / 综述 / 面试题 | 同上 | 命中 `papers/survey/interview/原理` |
| 数据集 / 纯模型权重 | 没有工程实现，做产品要另找代码 | topics 命中 `dataset/model-weights/papers` |
| 插件目录 / 索引站 | 是"链接集合"，不是可复用代码 | 命中 `directory/registry/catalog/collection/list of/目录` |
| Fork / 归档仓库 | 不是原创维护，或者已经停更 | GitHub 字段 `fork` / `archived` |

## 二、六条硬门槛（缺一不可）

| # | 门槛 | 阈值 | 理由 |
| --- | --- | --- | --- |
| 1 | AI 相关 | **官方简介**本身命中 AI 强信号（大模型 / Agent / RAG / 生成式 / 语音识别等）；仅 topics 堆砌 `llm`、`ai` 标签不算 | 榜单只收 AI / 大模型能力，不做通用软件榜；避免 gitleaks 这类"顺带支持 AI"的项目混进来 |
| 2 | 已被验证 | 星标 ≥ **800**，复刻 ≥ **40** | 星标说明有人关注，复刻说明真有人拿去用 |
| 3 | 仍在维护 | 最后提交距今 ≤ **120** 天 | 停更项目的接口、依赖会腐坏，不能当产品底座 |
| 4 | 不是新秀 | 仓库年龄 ≥ **150** 天 | 太新的项目定位和接口都会变，等它跑稳半年 |
| 5 | 说得清自己 | 官方简介 ≥ **20** 字符 | 简介都写不清的项目，无法判断能做成什么 |
| 6 | 允许商业化 | 必须声明许可证，且不是 `NOASSERTION` | 无许可证 = 法律上不可商用，进榜没有意义 |

> 许可证宽松度不设门槛，但会计入综合得分：MIT / Apache-2.0 / BSD / ISC / MPL 等宽松许可满分，
> GPL / AGPL 等有传染性的许可只给部分分，并在详情页标注"需确认"。

## 三、总量：不设上限

**榜单没有数量上限**，通过第二节硬门槛的项目全部收录，随候选池扩张而增长（当前 500 条，候选池 4000+ 时有 955 个合格项目）。
不做"配额削平"的原因：一旦限定总量，新合格项目就必须挤掉老项目，榜单会反复抖动，
而读者真正需要的是"所有合格项目都在这里，且按做产品的可能性排序"。

方向的多样性由**硬门槛 + 用途分类优先级 + 综合得分**自然调节，不再用配额硬切。
需要限定规模时用 `LIMIT`，语义是**按综合得分截断前 N 个**：

```bash
LIMIT=500 pnpm tsx scripts/fetch/rebuild-github.ts                    # 取分数最高的 500 个
LIMIT=500 QUOTA=1 pnpm tsx scripts/fetch/rebuild-github.ts             # 小规模试点：先按方向配额再补位
```

| 方向 | 试点配额 | 方向 | 试点配额 |
| --- | --- | --- | --- |
| 智能体 Agent | 12 | 写作 Writing | 3 |
| 编程 Coding | 7 | 效率 Productivity | 3 |
| AI 对话 | 5 | 数据分析 | 2 |
| 知识库检索 RAG | 5 | 营销 Marketing | 2 |
| 模型推理 Inference | 5 | 其他 Other | 2 |
| 图像生成 | 5 | 视频 Video | 4 |
| 语音与音频 | 4 | 自动化 Automation | 4 |

## 四、排序与最终取舍

1. 通过门槛的项目全部入榜，按**综合得分**（热度 15 + 增长 15 + 可开发性 20 + 商业化 30 + 活跃度 10 + 落地门槛 10）降序；
2. 入库后生成中文情报，用真实「上手难度」重算一次得分并重新排序；
3. 列表页固定**每页 20 条**，与总量无关。

得分只决定**顺序**，不决定**资格**——资格只看第二节。

## 五、用途分类的判定顺序

列表"用途"列和详情页标签都来自 `mapCategories(topics)`，**最多 3 个，第一个是主标签**。
判定顺序即优先级：**具体形态在前，智能体与泛对话在后**——
否则一个 `llm + agent + video` 的仓库会被标成"智能体"，整张榜单就只剩一个标签。

```
视频 → 图像生成 → 语音与音频 → 知识库检索 → 模型推理 → 编程开发
→ 写作 → 营销 → 数据分析 → 效率工具 → 自动化 → 智能体 → AI 对话 → 其他
```

结果校验（当前 500 条）：编程开发 184 · 知识库检索 86 · 模型推理 54 · 智能体 44 · 语音 35 ·
数据分析 24 · 自动化 17 · 图像生成 17 · 视频 13 · AI 对话 10 · 效率 7 · 营销 3 · 写作 2 · 其他 4。

## 六、中文要求

榜单面向中文读者，所有解读字段必须是中文：

- 列表"简介"列：中文一句话定位（大模型生成）
- 详情页"它是什么"：中文改写，不保留英文原简介
- 只允许保留的英文：项目名 `owner/repo`、编程语言名、许可证 SPDX 标识（如 MIT）
- 生成后若仍有英文残留，脚本会用 `zhWalk` 做二次替换（SaaS→订阅服务、API→接口等）

## 七、重复拉取的执行方式

```bash
# 0) 先看规模：只统计候选池和合格项目数，不写数据、不消耗 README/情报配额
pnpm tsx scripts/fetch/rebuild-github.ts --count

# 1) 按原则重建榜单（自动备份到 content/backup/，候选池缓存 6 小时；默认不限总量）
pnpm tsx scripts/fetch/rebuild-github.ts
#    强制重搜候选池：加 --refresh-cache
#    限定总量：LIMIT=500（按得分截断）；小规模试点加 QUOTA=1（走方向配额）
#    扩大候选池：SEARCH_PAGES=3（每条词取 3 页）、PER_PAGE=100（单页上限 100）

# 2) 生成中文情报（DeepSeek；已有情报的项目自动跳过，只烧新增项目）
pnpm tsx scripts/fetch/enrich-github-insight.ts
#    不要随便加 --force（会把全部项目重烧一遍）

# 3) 中文二次清洗（把残留缩写换成中文，可重复执行）
pnpm tsx scripts/fetch/enrich-github-insight.ts --repair

# 4) 补全贡献者 / 提交活跃 / 语言占比（可重复跑，缺什么补什么）
pnpm tsx scripts/fetch/fill-github-stats.ts
```

**限流提醒**：匿名调用每小时 60 次，`README + 贡献者 + 提交活跃 + 语言占比` 每个项目要 4 次请求，
不限总量时务必配置 `GITHUB_TOKEN`（`ghp_...`，5000 次/小时，足够上千个项目）。
脚本按配额自动降级：配额不足时只补 README，其余交给 `fill-github-stats.ts` 后续补齐。

判定结果会打印在日志里（`候选 N 个，通过原则 M 个` + 淘汰原因统计），
所以"某个项目为什么没进榜"永远可追溯。

## 当前榜单已知情况

- 榜单规模随候选池增长：当前收录 500 条（按综合得分从 955 个合格项目中截断），不再有硬上限；
- 每个项目要 4 次 GitHub 请求（README / 贡献者 / 提交活跃 / 语言占比），必须配 `GITHUB_TOKEN`，
  否则匿名每小时 60 次只够 15 个项目，需靠 `fill-github-stats.ts` 分批续补；
- 中文情报按项目逐个调用大模型，新增项目越多耗时越长，脚本支持中断后重跑（已有情报自动跳过）。
