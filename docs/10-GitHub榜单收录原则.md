# GitHub 榜收录原则（gh-rank-v1.5）

> 本文是**唯一口径**。每次重新拉取数据都按同一套判定执行，代码实现见
> `scripts/fetch/github-ranking-rules.ts`，执行脚本见 `scripts/fetch/rebuild-github.ts`。
> 换原则 = 升版本号（gh-rank-v1.5 / v2），并在本文"变更记录"里写清为什么改。

## 一句话原则

**一个项目能进榜，必须同时满足「AI 相关且可被二次开发」「真实活跃」「允许商业化」三个条件，能给出至少一个读者可以自己动手做的产品点子，并且**用很小的成本（一个人 / 一台机器 / 低月费）就能做出首版**；总量不设上限，合格即收录，按「小而美的机会」优先排序。**

榜单不服务的对象：想看论文、数据集、教程、模型权重的人。

榜单只服务一种读者——**想做点事的人**：创业者、AI 工具的重度使用者、互联网与科技从业者，
以及所有「手上没资源，但想做出点不一样的东西」的个人。他们来这里不是为了学习，
而是为了**抄一个能落地的起点**：看到别人的能力，想到自己能做的产品。

## 一、手工排除（不管数据多好看）

| 类型 | 为什么不要 | 判定 |
| --- | --- | --- |
| `awesome-*` / 清单 / 资源合集 | 没有可复用代码，无法做成产品 | 名称或简介命中 `awesome/curated list/...` |
| 教程 / 课程 / 书籍 / 笔记 / 路线图 | 是学习材料，不是底座 | 命中 `tutorial/course/book/learning/教程/入门/笔记` |
| 论文合集 / 综述 / 面试题 | 同上 | 命中 `papers/survey/interview/原理` |
| 数据集 / 纯模型权重 | 没有工程实现，做产品要另找代码 | topics 命中 `dataset/model-weights/papers` |
| 插件目录 / 索引站 | 是"链接集合"，不是可复用代码 | 命中 `directory/registry/catalog/collection/list of/目录` |
| Fork / 归档仓库 | 不是原创维护，或者已经停更 | GitHub 字段 `fork` / `archived` |

## 二、六条硬门槛（缺一不可）

| # | 门槛 | 阈值 | 理由 |
| --- | --- | --- | --- |
| 1 | AI 相关 | **官方简介**本身命中 AI 强信号（大模型 / Agent / RAG / 生成式 / 语音识别等）；仅 topics 堆砌 `llm`、`ai` 标签不算 | 榜单只收 AI / 大模型能力，不做通用软件榜；避免 gitleaks 这类"顺带支持 AI"的项目混进来 |
| 2 | 已被验证 | 星标 ≥ **800**，复刻 ≥ **40** | 星标说明有人关注，复刻说明真有人拿去用 |
| 3 | 仍在维护 | 最后提交距今 ≤ **120** 天 | 停更项目的接口、依赖会腐坏，不能当产品底座 |
| 4 | 不是新秀 | 仓库年龄 ≥ **150** 天 | 太新的项目定位和接口都会变，等它跑稳半年 |
| 5 | 说得清自己 | 官方简介 ≥ **20** 字符 | 简介都写不清的项目，无法判断能做成什么 |
| 6 | 允许商业化 | 必须声明许可证，且不是 `NOASSERTION` | 无许可证 = 法律上不可商用，进榜没有意义 |

> 许可证宽松度不设门槛，但会计入综合得分：MIT / Apache-2.0 / BSD / ISC / MPL 等宽松许可满分，
> GPL / AGPL 等有传染性的许可只给部分分，并在详情页标注"需确认"。

## 三、读者价值门槛（v1.4 新增，情报层硬要求）

项目本身合格还不够，**情报必须能让人产生一个新想法**。判定只有一条：

> 读者读完，能不能想起「这个我能拿来做点什么」。

落地为三问，缺一不可：

| # | 三问 | 合格标准 | 不合格的样子 |
| --- | --- | --- | --- |
| 1 | 能做成什么 | ≥ **3** 个具体产品形态（`buildIdeas.title` + `product`） | 「可以做企业服务」 |
| 2 | 卖给谁、怎么收钱 | 每个点子都写清 `audience`（具体人群/行业）+ `monetization`（带数字的定价） | 「面向企业，订阅收费」 |
| 3 | 值不值得动手 | ≥ **3** 步落地动作且绑定该项目独有能力 + 一句护城河判断 | 「先跑通再找场景」 |

代码执行：`checkIdeaValue()`（`scripts/fetch/github-ranking-rules.ts`，版本 `IDEA_RULES`）。

- LLM 首版不合格时，会带着"不合格原因"**补生成一次**；
- 补完仍不合格的条目照常入库，但日志标记 `读者价值仍不足`，便于人工精编补写
  （`scripts/fetch/curated-github-insights-*.ts`）；
- 这条门槛不影响「项目能否进榜」，只影响「这条情报是否算合格交付」——
  它把"收录"和"对读者有价值"分开，避免为了凑数把空话写进榜单。

## 四、总量：不设上限

**榜单没有数量上限**，通过第二节硬门槛的项目全部收录，随候选池扩张而增长（v1.4 起目标 800 条，v1.5 依次扩至 900 / 1000 / 1500 条，靠扩容候选池达成，不靠降低门槛）。

v1.4 扩容的具体做法：搜索词 76 → 116 条，新增三类词——

| 新增类别 | 为什么加 | 例子 |
| --- | --- | --- |
| 垂类生意 | 越具体的行业，越容易被一个人做成一门小生意 | `legal-tech`、`recruiting`、`invoice`、`real-estate`、`customer-support` |
| 分发形态 | 决定新玩家能不能低成本触达用户 | `chrome-extension`、`telegram-bot`、`shopify`、`wordpress`、`no-code` |
| 内容生产 | 自媒体与电商的素材刚需，付费意愿最直接 | `subtitle`、`video-editing`、`podcast`、`pdf-parsing`、`spreadsheet` |

**刻意不做的**：降低星标/复刻门槛来凑数。门槛一旦松动，混进来的就是"没人验证过的玩具"，
读者的第一反应会从"这个我能做"变成"这个没人用"，榜单价值直接归零。

不做"配额削平"的原因：一旦限定总量，新合格项目就必须挤掉老项目，榜单会反复抖动，
而读者真正需要的是"所有合格项目都在这里，且按做产品的可能性排序"。

方向的多样性由**硬门槛 + 用途分类优先级 + 综合得分**自然调节，不再用配额硬切。
需要限定规模时用 `LIMIT`，语义是**按综合得分截断前 N 个**：

```bash
LIMIT=500 pnpm tsx scripts/fetch/rebuild-github.ts                    # 取分数最高的 500 个
LIMIT=500 QUOTA=1 pnpm tsx scripts/fetch/rebuild-github.ts             # 小规模试点：先按方向配额再补位
```

| 方向 | 试点配额 | 方向 | 试点配额 |
| --- | --- | --- | --- |
| 智能体 Agent | 12 | 写作 Writing | 3 |
| 编程 Coding | 7 | 效率 Productivity | 3 |
| AI 对话 | 5 | 数据分析 | 2 |
| 知识库检索 RAG | 5 | 营销 Marketing | 2 |
| 模型推理 Inference | 5 | 其他 Other | 2 |
| 图像生成 | 5 | 视频 Video | 4 |
| 语音与音频 | 4 | 自动化 Automation | 4 |

## 五、排序：小而美的机会优先（v1.5 重写）

读者是普通创业者，**没有预算、没有团队、没有算力**。所以排序的第一问不是「这个项目多牛」，
而是「**一个人、一台机器、很少的钱，能不能靠它做出小而美、能收点钱的东西**」。

综合得分 `pps-v4` 的 8 个维度（权重合计 100）：

| 维度 | 权重 | 衡量什么 |
| --- | --- | --- |
| **轻启动机会** | **22** | 一个人能不能跑起来：体量甜区、有无重型依赖（k8s/多卡/分布式训练/集群运维）、是不是插件/机器人/单机/一键部署形态、MVP 月成本、出首版周期、上手难度 |
| **加工空间** | **18** | **加工之后能不能做出跟它不一样的东西**。它本身已是完成度很高的成品（有完整界面、开箱即用）→ 0-3 分，照抄只能做出一模一样的东西；产品形态固定 → 4-5 分；通用原材料，能嵌进完全不同的产品 → 6-10 分。由大模型读 README 判定（正则做不到，见下） |
| 商业化潜力 | 14 | 许可可商用 6 ＋ 这个领域有没有人付钱：pricing/订阅/企业版/商用授权 4 ＋ 作者有对外门面：独立域名 4、仅文档托管页 1 |
| 落地门槛 | 13 | 上手难度 6 ＋ 体量吃透 4 ＋ 是否需付费基础设施 2 ＋ 出首版周期 1 |
| 需求验证 | 12 | 热度饱和归一 6（1 万星即视为验证完成）＋ fork/star 比 4 ＋ 未结 issue 2 |
| 可开发性 | 7 | 描述/标签/许可/主流语言/README 完整度 |
| 维护活跃度 | 7 | 最近提交、近 4 周提交、贡献者规模（能不能长期依赖） |
| 增长动能 | 7 | 近 30 天真实星标增速；**无真实采样按中性 50 计，不用回填数据编造** |

### 为什么必须有「加工空间」（v1.7）

榜单读者不是来找「好项目」的，是来找**能加工出不一样产品**的原材料。

一个项目越完善、越活跃、越像成品，模型原本给它分越高；但反过来，**它已经做完的事，你再做一遍就是照抄**，别人也能马上复制。这才是榜单最该回答的问题：**加工之后，你能不能做出跟它不一样的东西？**

典型例子 `tomasz-tomczyk/crit`（本地 CLI 启动浏览器界面，审查 AI 编码代理产出的计划）：

| 维度 | 改造前 | 改造后 | 说明 |
| --- | --- | --- | --- |
| 加工空间 | — | 7.2 / 18 | 模型判定「它已占住『在浏览器里审查 AI 代理产出的计划与 diff』」，只能换人群或做周边 |
| 商业化 | 22 / 22（满分） | 10 / 14 | 「plans」曾被误判成付费订阅 |
| **总分** | **91.4（第 2，S）** | **78.0（A）** | 从「强推」降到「值得做」 |

### 为什么这一项必须用大模型判断，不能用关键词

试过用正则识别「成品 / 原材料」：

- `/api|sdk|cli|plugin|dashboard/` 这类词，1500 条里 **92% 命中**，等于白送分；
- 把范围收窄到 `web app|dashboard|desktop app` 后，命中只剩 91 条（6%），但 **crit 的描述里没有这些词**（它写的是「in the browser」），直接被判成「可当底座」，完全反了。

所以改为：让模型读 README + 已有中文情报，输出 `base`（它是什么形态）、`occupancy`（它自己占住了什么场景）、`space`（0-10）、`untapped`（它没做、你能做的方向）、`hook`（可接入的技术入口），脚本见 `scripts/fetch/enrich-github-derivative.ts`。

实测分布：均分 5.9、标准差 2.1、区间 2-9，是当前**唯一一个由模型判断、且方差显著的维度**。

### pps-v3 相对 pps-v2 修了什么（v1.6）

v2 上线后实测发现三个维度基本是常数，真正区分排名的只剩「轻启动」和「商业化」：

| 问题 | 实测证据 | v3 处理 |
| --- | --- | --- |
| 官网被当成商业化证据 | 用 `homepage` 非空直接加 6 分，80% 项目命中；其中 268 个是 github.io / readthedocs 文档站 | 独立域名 4 分、文档托管页 1 分；并明确「官网 ≠ 能赚钱」写进详情页 |
| 付费信号形同虚设 | v2 用 `/api|sdk|cli|docker|deploy/`，命中率 88%；v3 第一版用 `plans?` 又把 crit 的「agent plans（执行计划）」判成付费订阅 | 只认 pricing / subscription / billing / 企业版 / 商用授权 这类收费行为，明确排除 plans / price / self-host / managed |
| fork 绝对数 = 商业化验证 | 门槛要求 forks≥40，且 1500 条中 1400 条 forks≥100（93%），该子项无区分度 | 改用 fork/star 比，并挪进「需求验证」维度 |
| 增长动能用回填数据 | `backfillHistory` 按当前星标反推 30 天序列，1500 条全部是估算点，v2 据此算出的「+2.5%」是编的 | 回填点标记 `synthetic=true`，增速只统计真实采样，不足 7 天显示「—」 |
| 可开发性 83% 满分 | 只要「描述+标签+许可+语言+README」都有就满分，几乎全员命中 | 权重 13→8，并改为质量分（README 长度、代码示例） |
| 等级阈值虚高 | 分数被白送分抬到均值 75.2，S≥85 按「高于均值 10 分」定，导致 C 档占 43% | 按新分布重标：S≥80 / A≥76 / B≥70（约前 4% / 16% / 60%） |

**核心判断原则：** 这个榜衡量的不是「项目多优秀」，而是「**它作为原材料，能不能帮你做出一个有人愿意付钱的产品**」。
所以项目自己越完善、越商业化，对你反而越不一定是好事——已经在卖的，你只能跟它竞争或做它的周边，商业化项会因此扣分。

**重型项目的处理方式：不排除，但降权。**
命中 `kubernetes / k8s / helm / terraform / spark / 分布式训练 / 多卡 / 集群 / 微服务` 等多个信号的项目，
轻启动项扣 9-20 分；百万级体量的基础设施再扣 12 分。它们仍然可以进榜（作为技术参考），
但不会占据面向个人创业者的前几屏。

1. 通过门槛的项目全部入榜，按上表综合得分降序；
2. 入库后生成中文情报，用真实「上手难度 / MVP 成本 / 出首版周期」重算一次得分并重新排序；
3. 列表页固定**每页 20 条**，与总量无关。

得分只决定**顺序**，不决定**资格**——资格只看第二节。

## 六、用途分类的判定顺序

列表"用途"列和详情页标签都来自 `mapCategories(topics)`，**最多 3 个，第一个是主标签**。
判定顺序即优先级：**具体形态在前，智能体与泛对话在后**——
否则一个 `llm + agent + video` 的仓库会被标成"智能体"，整张榜单就只剩一个标签。

```
视频 → 图像生成 → 语音与音频 → 知识库检索 → 模型推理 → 编程开发
→ 写作 → 营销 → 数据分析 → 效率工具 → 自动化 → 智能体 → AI 对话 → 其他
```

结果校验（当前 500 条）：编程开发 184 · 知识库检索 86 · 模型推理 54 · 智能体 44 · 语音 35 ·
数据分析 24 · 自动化 17 · 图像生成 17 · 视频 13 · AI 对话 10 · 效率 7 · 营销 3 · 写作 2 · 其他 4。

## 七、中文要求

榜单面向中文读者，所有解读字段必须是中文：

- 列表"简介"列：中文一句话定位（大模型生成）
- 详情页"它是什么"：中文改写，不保留英文原简介
- 只允许保留的英文：项目名 `owner/repo`、编程语言名、许可证 SPDX 标识（如 MIT）
- 生成后若仍有英文残留，脚本会用 `zhWalk` 做二次替换（SaaS→订阅服务、API→接口等）

## 八、重复拉取的执行方式

```bash
# 0) 先看规模：只统计候选池和合格项目数，不写数据、不消耗 README/情报配额
pnpm tsx scripts/fetch/rebuild-github.ts --count

# 1) 按原则重建榜单（自动备份到 content/backup/，候选池缓存 6 小时；默认不限总量）
pnpm tsx scripts/fetch/rebuild-github.ts
#    强制重搜候选池：加 --refresh-cache
#    限定总量：LIMIT=500（按得分截断）；小规模试点加 QUOTA=1（走方向配额）
#    扩大候选池：SEARCH_PAGES=3（每条词取 3 页）、PER_PAGE=100（单页上限 100）

# 2) 生成中文情报（DeepSeek；已有情报的项目自动跳过，只烧新增项目）
pnpm tsx scripts/fetch/enrich-github-insight.ts
#    不要随便加 --force（会把全部项目重烧一遍）

# 3) 中文二次清洗（把残留缩写换成中文，可重复执行）
pnpm tsx scripts/fetch/enrich-github-insight.ts --repair

# 4) 补全贡献者 / 提交活跃 / 语言占比（可重复跑，缺什么补什么）
pnpm tsx scripts/fetch/fill-github-stats.ts
```

**限流提醒**：匿名调用每小时 60 次，`README + 贡献者 + 提交活跃 + 语言占比` 每个项目要 4 次请求，
不限总量时务必配置 `GITHUB_TOKEN`（`ghp_...`，5000 次/小时，足够上千个项目）。
脚本按配额自动降级：配额不足时只补 README，其余交给 `fill-github-stats.ts` 后续补齐。

判定结果会打印在日志里（`候选 N 个，通过原则 M 个` + 淘汰原因统计），
所以"某个项目为什么没进榜"永远可追溯。
