## 0. 一句话结论

**六个榜的数据从"仓库 JSON"迁到 D1，页面从"构建期内联"改为"运行时按身份裁决"，R2 只承担大字段与归档。**

三件事同时发生：

1. **存储换位**：D1 成为唯一真相，仓库不再存数据
2. **渲染换位**：页面由 Worker 请求时组装，不再全量预渲染
3. **权限换位**：付费内容不再"藏在产物里"，而是"根本没被查询"

## 3. 存储职责边界

判断依据只有一条：**要不要按它过滤或排序。**

| 层 | 存什么 | 能查询 | 计费 |
|---|---|---|---|
| **D1** | 卡片字段、结构化详情、白名单、版本、变更日志 | ✅ SQL | 按行读/写 |
| **R2** | readme、原始采集响应、D1 备份 | ❌ 只能按 key 取 | 存储 + 操作，无出口费 |
| **Cache API** | 渲染后的 HTML | ❌ | 免费，可随时失效 |

**R2 不是缓存。** 它是持久化对象存储，丢了就是永久丢失。缓存是 `Cache-Control` + `caches.default`，两者不能互换。

具体分配：

| 数据 | 去哪 | 理由 |
|---|---|---|
| `judge`（stars、更新时间、license） | D1 `board_items` | 候选页要排序筛选 |
| 卡片展示字段 | D1 `board_items.card` | 列表页要分页排序 |
| 结构化详情 | D1 `board_item_details` | 详情页一次查一行 |
| **github readme（12 MB）** | **R2** | 只读不查，塞 D1 会拖慢每一行 |
| 原始采集响应 | R2 `raw/` | 纯归档 |
| 判决证据、字段体检 | D1 `board_item_evidence` | 只有后台读，与渲染路径物理隔离 |
| 每周全库导出 | R2 `backup/` | 备份不能放在被备份的库里 |

## 4. 数据模型

新增 **12 张表**（内容 6 + 治理 6），迁移文件 `apps/api/migrations/0011_boards.sql`。

### 4.1 内容表（6 张：工作区 3 + 已发布 3）

```sql
-- ① 榜单注册
CREATE TABLE boards (
  board      TEXT PRIMARY KEY,   -- tools/github/trends/models/opps/digest
  title      TEXT NOT NULL,
  policy     TEXT NOT NULL,      -- JSON：付费策略快照
  sort_mode  TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);

-- ② 卡片态：列表页 / 首页 / 筛选 API 专用
CREATE TABLE board_items (
  board      TEXT NOT NULL,
  item_key   TEXT NOT NULL,      -- domain / owner-repo / slug / model-id
  status     TEXT NOT NULL,      -- candidate / enriched / rejected
  name       TEXT NOT NULL,
  url        TEXT,
  cats       TEXT,               -- JSON array
  judge      TEXT,               -- JSON：采集期判定字段（约 200B）
  card       TEXT,               -- JSON：富化后卡片字段（1–3KB）
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (board, item_key)
);
CREATE INDEX idx_items_status ON board_items (board, status, updated_at DESC);

-- ③ 工作区详情
CREATE TABLE board_item_details (
  board    TEXT NOT NULL,
  item_key TEXT NOT NULL,
  detail   TEXT NOT NULL,        -- JSON：10–40KB
  PRIMARY KEY (board, item_key)
);

-- ③b 已发布快照：带 version，保留最近 3 期（详见 §4.4）
CREATE TABLE board_listed (
  version  TEXT NOT NULL,        -- 2026-11-10T12:00
  board    TEXT NOT NULL,
  item_key TEXT NOT NULL,
  rank     INTEGER NOT NULL,
  score    REAL NOT NULL,
  tier     TEXT NOT NULL,
  name     TEXT NOT NULL,
  url      TEXT,
  cats     TEXT,
  card     TEXT,
  PRIMARY KEY (version, board, item_key)
);
-- 查询永远带 version 条件，索引必须以 version 打头，否则退化为全表扫描
CREATE INDEX idx_listed_rank ON board_listed (version, board, rank);

CREATE TABLE board_listed_details (
  version  TEXT NOT NULL,
  board    TEXT NOT NULL,
  item_key TEXT NOT NULL,
  detail   TEXT NOT NULL,
  PRIMARY KEY (version, board, item_key)
);

-- ④ 证据态：只有后台读
CREATE TABLE board_item_evidence (
  board     TEXT NOT NULL,
  item_key  TEXT NOT NULL,
  verdict   TEXT,
  gaps      TEXT,
  raw_ref   TEXT,                -- R2 路径
  PRIMARY KEY (board, item_key)
);
```

**为什么不合并 detail**：SQLite 是行存，`SELECT *` 会连 30 KB 的 detail 一起读。列表页查 60 行就拖动 1.8 MB。拆表后列表只碰 1–3 KB 的 card。

### 4.2 治理表（6 张）

```sql
-- ⑤ 发布快照：只存名单，不存数据，永远便宜
CREATE TABLE board_releases (
  version     TEXT PRIMARY KEY,  -- 2026-11-10T12:00
  board_scope TEXT NOT NULL,     -- JSON
  stats       TEXT NOT NULL,     -- JSON：各榜条数
  allowlist   TEXT NOT NULL,     -- JSON：这期免费名单
  actor       TEXT NOT NULL,
  applied     INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL
);

-- 永久保留的"名单"。存 name 才能回答"上期第 37 名叫什么"——
-- 工作区的 name 可能已改，只有快照能还原当时的名称
CREATE TABLE board_release_items (
  version  TEXT NOT NULL,
  board    TEXT NOT NULL,
  item_key TEXT NOT NULL,
  rank     INTEGER NOT NULL,
  tier     TEXT,
  name     TEXT NOT NULL,
  PRIMARY KEY (version, board, item_key)
);

-- ⑥ 变更审计：替代 git diff
CREATE TABLE board_changes (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  version    TEXT NOT NULL,
  board      TEXT NOT NULL,
  item_key   TEXT NOT NULL,
  action     TEXT NOT NULL,      -- add/update/drop/restore
  diff       TEXT,               -- {"name":{"from":"x","to":"y"}}
  applied    INTEGER NOT NULL DEFAULT 0,
  actor      TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE INDEX idx_changes_version ON board_changes (version, board);

-- ⑦ 免费名单：当前生效值（后台增删条目，立即生效）
CREATE TABLE board_allowlist (
  board    TEXT NOT NULL,
  item_key TEXT NOT NULL,
  note     TEXT,
  added_at INTEGER NOT NULL,
  added_by TEXT NOT NULL,
  PRIMARY KEY (board, item_key)
);

-- ⑧ 富化质量报告
CREATE TABLE enrich_reports (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  job_id     TEXT NOT NULL,
  board      TEXT NOT NULL,
  scope      TEXT NOT NULL,      -- {"selected":500,"enriched":487}
  report     TEXT NOT NULL,      -- {"readme":{"empty":12,"total":487}}
  created_at INTEGER NOT NULL
);

-- ⑨ 全局配置
CREATE TABLE app_config (
  key        TEXT PRIMARY KEY,
  val        TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

**两张 allowlist 表分工不同，不要混用：**

| 表 | 语义 | 写入时机 | 读取用途 |
|---|---|---|---|
| `board_allowlist` | **当前生效**的免费名单 | 后台增删条目，即时生效 | 渲染时判断 `unlocked` |
| `board_releases.allowlist` | 某一期的**名单快照**（JSON） | 发布时自动写入 | 仅用于审计与回滚对照 |

渲染**一律读 `board_allowlist`**。若读快照，改一次名单就得重新发布一期，失去“即时生效”的意义。

### 4.4 版本机制：发布不覆盖，保留最近 3 期

**核心约束：任何一次发布都不能改动上一期的数据。** 这决定了表结构必须带 `version` 维度。

版本分三层，各管一件事：

| 层 | 表 | 保留 | 体积 | 作用 |
|---|---|---|---|---|
| **数据** | `board_listed` + `board_listed_details` | **最近 3 期** | 3 × 46 MB ≈ 138 MB | 回滚后还能看到完整页面 |
| **名单** | `board_release_items` | 永久 | 60 B/条 × 3000 × N | 查"上期第 37 名是谁"，永不删除 |
| **审计** | `board_changes` | 永久 | 变更行数，极少 | 谁在哪一期改了哪个字段 |

**为什么不无限保留数据**：138 MB 是 3 期，10 期就是 460 MB。而真正需要"完整历史"的场景几乎没有 —— 你要的是"上期第 37 名是谁"，这由 `board_release_items` 永久回答，它只存 `key + rank`。

#### 发布：写进新 version，绝不动旧 version

```sql
-- ① 卡片+排名：由 publish 脚本在 Actions 里算好（TS 口径唯一），批量写入新 version
--    3000 行分 75 批，约 5–10 秒，旧 version 完全不受影响
INSERT INTO board_listed
  (version, board, item_key, rank, score, tier, name, url, cats, card)
VALUES ('2026-11-10T12:00', 'tools', 'openai.com', 1, 92.4, 'core', ...);

-- ② 详情：只复制「本次上榜」的条目，不是所有富化过的候选
--    富化 2000 个但只上榜 1500 时，落榜者的 detail 不该进快照
INSERT INTO board_listed_details (version, board, item_key, detail)
SELECT '2026-11-10T12:00', d.board, d.item_key, d.detail
FROM board_item_details d
WHERE d.board = 'tools'
  AND d.item_key IN (
    SELECT item_key FROM board_listed
    WHERE version = '2026-11-10T12:00' AND board = 'tools'
  );

-- ③ 名单快照（带 name，永久保留）
INSERT INTO board_release_items (version, board, item_key, rank, tier, name)
SELECT version, board, item_key, rank, tier, name
FROM board_listed WHERE version = '2026-11-10T12:00';
```

**④ 切换：三句必须放进同一个 `db.batch()`。** D1 没有交互式事务，`batch` 才是原子的。若先标记 `applied` 再单独切指针，中途失败会留下“已算发布、线上还是旧版”的脏状态，且清理逻辑会把它当作有效版本：

```ts
const v = "2026-11-10T12:00";
await db.batch([
  db.prepare("UPDATE board_releases SET applied=1 WHERE version=?").bind(v),
  db.prepare("UPDATE board_changes  SET applied=1 WHERE version=?").bind(v),
  db.prepare("UPDATE app_config SET val=?, updated_at=? WHERE key='config.current_version'")
    .bind(v, Date.now()),
]);
// 这一批提交前，线上读到的仍是旧版本
```

```sql
-- ⑤ 只删「已生效 且 超出保留名额」的版本
DELETE FROM board_listed_details
WHERE version IN (
  SELECT version FROM board_releases
  WHERE applied = 1
    AND version NOT IN (
      SELECT version FROM board_releases WHERE applied = 1
      ORDER BY created_at DESC LIMIT 3
    )
);
DELETE FROM board_listed
WHERE version IN (
  SELECT version FROM board_releases
  WHERE applied = 1
    AND version NOT IN (
      SELECT version FROM board_releases WHERE applied = 1
      ORDER BY created_at DESC LIMIT 3
    )
);
```

**不能写成 `version NOT IN (最近 3 期)`。** 那样会把还没发布的草稿一起删掉 —— 运营准备好下期数据等确认，被一次无关的发布清空，而且不会报错。

实测（4 期已生效 + 1 期草稿 `draft`）：

| 写法 | 结果 |
|---|---|
| `NOT IN (最近 3 期)` | v1 删、v2/v3/v4 保留、**`draft` 被误删** ❌ |
| `IN (已生效且超额)`（本方案） | v1 删、v2/v3/v4 保留、**`draft` 保留** ✅ |

**读取永远带当前版本**，这是唯一的查询入口：

```sql
SELECT * FROM board_listed
WHERE board = ? AND version = (
  SELECT val FROM app_config WHERE key = 'config.current_version'
)
ORDER BY rank LIMIT 20 OFFSET ?;
```

#### 回滚：改一个字段

```sql
UPDATE app_config SET val = '2026-10-10T12:00'
WHERE key = 'config.current_version';
```

秒级生效，不需要搬数据、不需要重新计算、不需要重建站点。**这是"保留旧版本"换来的唯一价值，也是它值得占 138 MB 的原因。**

#### 三个必须守住的边界

| 边界 | 后果 | 防护 |
|---|---|---|
| 发布前不校验旧版本存在 | 新版本写入后才发现无基线，无法对比 | 发布脚本第一步 `SELECT` 当前版本，不存在直接失败 |
| 清理时用 `created_at` 而非 `applied` | 草稿版本占用存活名额 | 只统计 `applied=1` 的版本 |
| 回滚到已被清理的版本 | 指针指向空数据，页面 500 | 切换前校验目标版本行数 > 0，为 0 则拒绝 |

最后一条尤其重要：**`board_release_items` 永久保留，所以"名单"永远查得到，但"详情"只能回溯 3 期。** 这是明确的取舍，要在后台回滚面板上标注清楚。

| 榜 | `item_key` | 特殊处理 | 难度 |
|---|---|---|---|

| **opps** | `slug` | 人工策展无脚本；`evidence[].ref` 跨表校验改为查 D1 | ★ |
| **digest** | `YYYY-MM-DD` | `raw/`、`state/` 是过程数据，不入主表 | ★★ |
| **tools** | `domain` | 白名单 + 付费墙在此榜首开 | ★★★ |

## 6. 写入链路

对应运营流程的四个阶段，全程在 GitHub Actions 内执行，通过 D1 HTTP API 写入。

```
┌── 阶段 1 · 采集 ──────────────────────────────┐
│ [采集按钮] 参数：数据源 / 目标数量              │
│   ↓                                          │
│ Actions: fetch-*.yml（只收 job_id）           │
│   ↓                                          │
│ 拉候选 → 只取「判定字段」→ 规则过滤              │
│   ↓                                          │
│ D1: board_items status=candidate judge={...} │
└──────────────────────────────────────────────┘
              ↓ 人工圈选 部分/全部
┌── 阶段 2 · 富化 ──────────────────────────────┐
│ [富化按钮] 选中 N 条 → job.params 存 key 列表   │
│   ↓                                          │
│ Actions: enrich-*.yml                        │
│   ↓                                          │
│ 补齐全字段（含 LLM）                            │
│   ↓                                          │
│ 官网截图（桌面 1280 / 移动 390）                 │
│   ↓                                          │
│ 结构化 → D1: status=enriched, card=, detail=  │
│ 大文本 → R2: readme/{owner-repo}.md           │
│ 截图   → R2: {domain}.png / {domain}-mobile.png│
│   ↓                                          │
│ 质量报告 → D1: enrich_reports                 │
└──────────────────────────────────────────────┘
              ↓ 人工看报告，再圈选
┌── 阶段 3 · 预演（只读，不碰线上）────────────────┐
│ [计算变化] → 对比 enriched vs listed           │
│   ↓                                          │
│ D1: board_changes applied=0（草稿）           │
│   ↓                                          │
│ 后台展示：+12 / -3 / ~47 名次变动              │
└──────────────────────────────────────────────┘
              ↓ 人工确认
┌── 阶段 4 · 发布（原子）───────────────────────┐
│ [发布按钮] → Actions: publish-*.yml           │
│   1. 重算 rank / score / tier（shared）        │
│   2. 写 board_listed（新 version，不动旧版）    │
│   3. board_release_items 名单快照              │
│   4. board_changes 标记 applied=1             │
│   5. UPDATE current_version ★原子切换          │
│   6. 清理超过 3 期的旧 version                 │
└──────────────────────────────────────────────┘
```

### 6.1 采集期必拿字段（判定用）

以下字段**全部来自同一个 API 响应**，采集 2000 个 = 2000 次请求，无多余调用：stars / forks、pushed_at、archived / fork、license、language、description。

### 6.2 富化期才取的字段（贵，按需）

readme 全文、提交历史、语言分布、contributors、AI 洞察 / playbook。

官网截图也只在富化期拍（桌面 1280×800 + 移动 390×844，Playwright headless）：不花钱，
但每站约 8–15 秒，且图要进 R2 桶 `horizons-archive`（平铺文件名，Worker 拦截
`/screenshots/*` 从桶里取，构建产物保持轻量）。图片已存在则跳过，重复富化不会重拍；
上传失败只告警，用 `scripts/admin/upload-screenshots-r2.ts` 补传。

一个候选的富化成本约为采集的 **5–10 倍**。若 2000 个候选只富化 500 个，总成本降到 1/4 —— 这是整个流程的经济学核心。

> **硬约束：`judge` 必须完整落库，不能只留在 Actions 内存里。** 人工筛选是异步的（今天采明天看），没有 judge 就无法在后台按 stars 排序、按语言筛选。

### 6.3 三个实现细节

1. **workflow 只收 `job_id`**：圈选 500 个 key 会超 `workflow_dispatch` 输入长度，key 列表写进 `jobs.params`，workflow 自己去 D1 读。
2. **任务结果必须回写**：现有三张 `*_jobs` 的 `summary` 没有任何写入点，后台看不到最终结果。补 `POST /admin/jobs/:id/callback`（ADMIN_TOKEN 校验）。
3. **发布不依赖事务**：D1 无交互式事务，只有 `batch` 原子。靠"先写新 version → 最后切指针"保证一致性。

## 7. 读取链路

### 7.1 页面请求

```
GET /tools/openai.com
  ↓
Site Worker
  ├─ /data/* /content/* /_private/* → 404 硬墙
  ├─ /pricing /terms /privacy       → ASSETS 直出
  ├─ 列表页 /tools /github /trends  → 查 D1 卡片态 → 渲染
  │                                    Cache-Control: public, 300s
  └─ 详情页 /tools/:domain
       ├─ domain 归一化（小写 / 去尾斜杠 / 解码）
       ├─ 在 allowlist？──是──→ 查 detail → FULL
       │                          public, 300s
       ├─ session 有效且 pro？──是──→ FULL
       │                              private, no-store
       └─ 都不是 ──→ LOCKED（★ 根本不查 detail 表）
```

**三条铁律：**

1. `LOCKED` 分支**不查** `board_listed_details`。不是"查了不渲染"，是"不查"
2. allowlist 读失败时**全部锁**，绝不 fallback 到放行
3. 会员版 `full` **绝不能加 `public` 缓存头** —— 唯一能造成全站泄露的配置

#### 灰度期必须有双读分支

阶段 1–3 期间，六个榜是**逐个**迁到 D1 的。所以每次读取都要先问一句“这个榜现在读哪儿”：

```ts
// apps/api/src/lib/versions.ts
export async function resolveSource(db: D1Database, board: Board): Promise<"d1" | "file"> {
  const row = await db.prepare("SELECT val FROM app_config WHERE key=?")
    .bind(`data_source.${board}`).first<{ val: string }>();
  return row?.val === "d1" ? "d1" : "file";   // 缺配置 / 读失败 一律回落到 file
}

export async function currentVersion(db: D1Database): Promise<string | null> {
  const row = await db.prepare("SELECT val FROM app_config WHERE key='config.current_version'")
    .first<{ val: string }>();
  return row?.val || null;
}
```

读取路径统一成：

```
board → resolveSource() ─┬─ "file" → 读 content/*.json（迁移期兜底）
                         └─ "d1"   → currentVersion() → 查 board_listed
```

> **注意 fallback 方向与 allowlist 相反**：数据源读失败要回落到 `file`（有数据总比 500 好），而 allowlist 读失败必须回落到「全锁」（没权限判断就当没权限）。两个方向不能抄错。

### 7.2 筛选 API

`public/data/*.json` 停发后，列表筛选走服务端：

```
GET /api/boards/:board/items?cats=&sort=&page=&q=
  ├─ 无 session → 只返回 allowlist 内条目 + 公开字段
  │                { rank, name, url, cats, tier, unlocked }
  ├─ session 且 pro → 全部卡片字段
  │                   + { visits, mom, organic, dr, score }
  └─ Cache-Control: private, no-store
```

首屏 SSR 直接读 D1，不绕内部请求。

**灰度期已落地的版本**（`apps/api/src/routes/boards.ts`，付费墙前）：

```
GET /api/boards/:board        → { board, source, version, total }
GET /api/boards/:board/items  → { board, source, version, total, page, size, pages, items[] }
     ?q=&cat=&tier=&sort=rank|score|name&page=1&size=20
```

四条约束，每条都对应一个具体的坑：

1. **只返回当前生效版本**（`config.current_version`），不暴露历史版本；历史与回滚只走后台。
2. **没切流时返回 409 `{ error: "source_is_file", source: "file" }`**，不返回空数组 —— 空数组在前端等价于「这个榜是空的」，会把一次配置缺失渲染成线上空榜。
3. **排序只认三个白名单值**，全部是固定 SQL 片段；其余参数一律参数绑定，`cat` 用 `%"<cat>"%` 的带引号片段匹配，避免 `Video` 命中 `Video Gen`。
4. **`Cache-Control: public, max-age=30`**：切流/发布后最多 30 秒可见，不做失效逻辑。**上付费墙时必须改成 `private, no-store`**，否则一次 public 缓存就是全站泄露。

**接前端之前必须解决的一件事**：`card` 现在存的是**源实体**（`AITool` / `GitHubRepo` / `AITrend` / 模型 / 情报原文）去掉大字段，不是列表行（`ToolRow` 那种含预渲染 `h` 的形态）。站点筛选脚本的渲染方式是 `row.innerHTML = item.h`，所以前端改成调 API 之前必须先决定它吃哪一种：

| 做法 | 改动 | 代价 |
|---|---|---|
| 发布时把 `card` 换成列表行（含 `h`） | 把 `artifacts.ts` 的 `toToolRow` 等四个函数提到 `apps/site/src/lib/rows.ts`，构建与发布共用；然后把六个榜重灌一遍 | 一次性数据语义迁移，`card` 从约 3KB 降到约 1.5KB，前端零改动 |
| 前端从 `card` 现算列表行 | 把 `traffic.ts` / `trends.ts` 等派生函数搬进浏览器产物 | `trends` 的 `series` 已不进卡片、`spark` 算不出来，这条路走不通 |

所以走第一条。但它会改 `card` 的语义，要和「详情外置 / 按条鉴权」一起设计，不能单独发。

### 7.3 类型焊死泄露

**付费边界是「指标与详情」，不是「名称」。** 锁定页必须能渲染标题和一句话介绍，否则连 `<title>` 都没有，SEO 直接废掉。

```ts
// packages/shared/src/view.ts

/** 公开字段：列表页 / 锁定页 / SEO 全依赖它 */
export interface PublicTool {
  domain: string;
  name: string;          // 锁定页 <title> 与 H1 必需
  tagline: string;       // 一句话介绍，构成锁定页的差异化正文
  cats: string[];
  tier: "core" | "watch";
  updatedAt: number;
}

/** 付费字段：只有 FULL 分支能拿到 */
export interface ProTool extends PublicTool {
  rank: number;
  score: number;
  monthlyVisits: number;
  momGrowth: number;
  organicShare: number;
  directShare: number;
  dr: number;
  detail: ToolDetail;    // 10–40 KB 结构化详情
}

export function getPublicTool(db: D1Database, d: string): Promise<PublicTool | null>;
export function getProTool(db: D1Database, d: string): Promise<ProTool | null>;
```

锁定页模板写 `tool.monthlyVisits` 会**编译失败**，不是"记得别写"。而 `tool.name` 是允许的 —— 它是公开字段。

### 首次线上运行前的四个硬约束

这批代码只在本地 sqlite 上演练过，而本地和真 D1 有几处行为不同。逐条核对后，改掉了四个会**直接失败**或**静默出错**的地方：

| 问题 | 后果 | 修法 |
|---|---|---|
| 分批按 100 行，`board_listed` 10 列 = 1000 个绑定参数 | D1 每条查询限 100 个参数，**首次发布必然报错**。本地 sqlite 上限是 32766，演练永远发现不了 | `chunkForSpec()` 按列数反推每批行数 |
| 版本号精确到分钟 | 同一分钟内连着发 models 和 digest，后一个被当成「重发」跳过，**数据静默丢失且无报错** | 改秒级；并且要「本榜在该版本里已有数据」才判定为重发 |
| `collect/index.mjs` 里 `cwd` 多退了一级 | 同步命令在仓库外执行，必然失败；失败又被 `try/catch` 吞成一行告警 | 直接用 `core.mjs` 的 `ROOT` 常量 |
| `pruneVersions` 只保留「最新 3 期已生效」 | 回滚到旧版本后再发布，可能把当前正在被读的版本删掉，**线上瞬间空榜** | 强制把 `current_version` 加进保留列表 |

还有两处按字节算的地方：详情行大小校验、分块阈值原本用 `JSON.stringify().length`（这是**字符数**），中文实际占 3 字节，上限判断会松三倍。已统一改成 `TextEncoder` 算真实字节。

顺带把请求数压下来：github 一次发布产生 441 条语句，逐条发就是 441 次 HTTP 往返，几十秒且容易撞 429。现在归并成 4 次 `batch()` 调用（内部再按 50 条/请求切），实际约 10 次请求，且整批在服务端原子执行。

### 首次运行检查清单

按顺序做，每步都能独立确认成败：

1. **本地建表**：`pnpm d1 migrations apply horizons-db --local` —— 确认 12 张表建好（`board_listed` / `board_releases` / `board_changes` / `board_release_items` 是关键四张）
2. **远程建表**：`pnpm d1 migrations apply horizons-db --remote` —— 远程库不加表，后面所有写入都会失败
3. **本地试发一个榜**：`pnpm tsx scripts/admin/publish-tools.ts --dry --no-d1` —— 只验算，不写库
4. **远程真发一个榜**：`pnpm tsx scripts/admin/publish-tools.ts` —— 需要 `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID`
5. **核对结果**：`pnpm d1 execute horizons-db --remote --command "SELECT version, board, COUNT(*) FROM board_listed GROUP BY version, board"`
6. **看后台**：打开 `/admin` → 「榜单版本」页签，确认版本卡片里的条数与第 5 步一致

第 4 步是最关键的一次验证：它会同时验证参数上限、batch 提交、继承上期其余榜、变更记录四件事。

### 阶段 3 的一个实测结论：筛选 API 比预想贵

原本把「筛选 API」和「后台榜单管理」放在同一阶段，实测后发现前者成本被低估了。

站点列表页的筛选脚本（`tool-filter.ts` 等 5 个）**不渲染 DOM，而是直接插入构建期生成的 HTML 片段**：

```js
row.innerHTML = item.h;   // h 是构建时渲染好的整行 <a>…</a>
```

这份 `h` 在 `content/dist/<board>/index.json` 里，是 Astro 组件在构建时产出的结果，含图标引用、可见性快照、class 顺序。

改成 API 有两条路，代价差别很大：

| 方案 | 服务端要做什么 | 代价 |
|---|---|---|
| 返回预渲染 HTML | 把 Astro 组件的渲染逻辑搬进 Worker | 同一种渲染维护两遍，改样式两边都得改，且图标/资产路径在 Worker 里不可用 |
| 返回结构化字段 | 前端把「插入 HTML」改成「拼 DOM」 | 5 个榜的列表渲染全部重写，首屏是构建期出的静态 HTML，还要保证和客户端渲染结果一致 |

所以拆开推进：

- **后台榜单管理**（已完成）：`/api/admin/boards/*` + `admin.astro` 的「榜单版本」页签。纯增量，不改站点任何渲染，提供版本列表、条目核对、变更记录、回滚、数据源开关。
- **筛选 API**（已完成，仅服务端）：`GET /api/boards/:board` 与 `GET /api/boards/:board/items`，见 §7.2。纯增量，站点仍读 `public/data`，两条路径并存。
- **前端接入与停发 `public/data`**（未开始，与付费墙一起做）：见 §7.2「接前端之前必须解决的一件事」。

判断依据：筛选 API 的收益主要是首屏体积和防抓取，风险却是动到五个榜的列表渲染。在付费墙（阶段 4）落地前，这个交换不划算。

**实际推进顺序与原计划不同**：先接了 tools / github / trends —— 这三个都有现成的独立发布入口（`publish-*.ts`），改造成本最低，而且正好覆盖三种发布形态：

| 形态 | 代表 | 特点 |
|---|---|---|
| 增量追加 | tools | 新条目追加、存量下榜，名次靠 `compareByToolScore` 重排 |
| 全量重排 | github | 每日重新打分排序，1500 条整体位移 |
| 关键词榜 | trends | 别名不占名次，`series` 不进卡片 |

剩下三个（models / opps / digest）没有独立的「发布」动作，接入点在各自的上游流程里，已全部接好：

| 榜 | 脚本 | 触发点 |
|---|---|---|
| models | `publish-models.ts` | `scripts/collect/index.mjs` 落盘后自动调用 |
| opps | `publish-opps.ts` | 无上游（人工策展），`workflow_dispatch` 手动触发 |
| digest | `publish-digest.ts` | `scripts/fetch/daily/build.ts` 写档后自动调用 |

三个脚本共用 `board-sync.ts`，只负责构造 `PublishRow[]`：名次口径一律复用站点侧的同一个函数（`overallScore` / `opportunityScore`），不在脚本里另写一遍排序公式 —— 否则页面名次和库里名次迟早对不上。

### ⚠️ 版本是全局快照，必须继承其余榜

这是实现时最容易踩空的一处，单独记录：

读取永远是 `WHERE version = (SELECT config.current_version) AND board = ?`，也就是**一个版本号对应一份全量快照**。而六个榜的更新节奏完全不同（github 每天、models 每周、opps 每周）。

如果发布 github 时只写 github、然后切指针，其余五个榜在新版本里一行都没有 —— 读者刷新一下，五个榜全空，而且没有任何报错。

所以 `publishBoard()` 在写本次数据前，先把上一版里**其余榜**整榜复制进新版本：

```sql
INSERT INTO board_listed (version, board, item_key, ...)
SELECT ?, board, item_key, ...
FROM board_listed WHERE version = ? AND board != ?
ON CONFLICT (version, board, item_key) DO NOTHING;
```

用 `INSERT ... SELECT` 在库内搬，不走网络：1500 行也是毫秒级，SQL 文本本身很短，不触 D1 的单语句大小限制。

连发三榜的实测结果（github → models → digest）：

| 版本 | 内容 | 说明 |
|---|---|---|
| v1 | github 3 | 首次发布，无继承 |
| v2 | github 3 + models 2 | models 继承 github |
| v3 | github 3 + models 2 + digest 1 | digest 继承前两榜 |

`board_scope` 与 `stats` 也在发布末尾按本版本实际含有的榜回填，不是只写本次那一个。

### 增量发布（默认）：只写变化的行

全局快照的代价是**每次发布都要重写全库**。按免费版 D1 每天 10 万 `rows_written` 算：

| 环节 | 行数 | 每次发布约耗 |
|---|---|---|
| 继承其余五个榜（github 1500 + trends 487 + models 366 + opps 5 + digest 24） | 2,382 | 21,000 |
| 本榜全量重写（tools 203 行 × 三种索引） | 203 | 1,800 |
| 剪枝：删掉一个旧版本 | 2,585 | 15,500 |
| **合计** | | **≈ 3.8 万** |

也就是说**一天点两次「更新榜单」就见底**。而运营批量刷新 30 条数据，真正变化的可能只有 30 行。

所以 `publishBoard()` 旁边多了 `patchBoard()`（`scripts/admin/publish-board.ts`），现在它是**默认路径**：

1. 读当前生效版本的 `board_listed`（不读详情正文，只读 `length(CAST(detail AS BLOB))`）
2. 逐行比对 rank / score / tier / name / url / cats / card / variant_of / 详情字节数
3. 只对新增行、变化行做 UPSERT，对下榜行按 key DELETE，其余一行不动
4. **不建新版本、不继承其它榜、不剪枝、不动指针**

同一批 30 条的刷新从 3.8 万降到几百次写。

代价（用之前必须知道）：

- **不产生新版本**：后台版本列表看不到这一次，回滚也回不到这次之前。需要留快照的重大改版（新增大量条目、换口径）仍走完整发布。
- **不是全有或全无**：分批提交，中途失败会留下部分更新的线上数据。所有语句都是 UPSERT / 按 key DELETE，重跑一次即收敛。
- 条数骤降 10% 以上会直接拒绝，防止误传局部列表把整榜删光（确需缩减加 `--allow-shrink`）。

谁在用：**所有入口默认都是增量** —— 后台四榜发布按钮、`publish-github/tools/trends/digest/opps`、`collect` 采集、`fetch-models` 定向刷新都直接走 `patchBoard`。

要完整发布必须显式指定：

| 入口 | 方式 |
|---|---|
| 后台 | 在 Actions 里手动 Run workflow，把 `patch` 传 `0` |
| 命令行 | 加 `--full` |

兜底：当前版本里这个榜一行都没有时（新库、新榜首次上线、`data_source` 刚从 file 切到 d1），自动回落成完整发布，先把版本骨架建出来。

### 全量发布：一次固化全部榜单

增量不推进版本号，跑久了版本列表会停住、也没有可回滚的基线。后台「榜单版本」页上方有**全量发布（重建版本）**：

- `POST /api/admin/boards/rebuild`，body 必须带 `{ confirm: "FULL" }`（前端让操作员手打「全量」才发得出来）
- 把当前版本的三张表（`board_listed` / `board_listed_details` / `board_release_items`）用 `INSERT ... SELECT` 搬到新版本号下，同批原子提交，再切指针、剪枝、清掉历史空壳版本
- **不重跑六条发布流水线**：数据已经在库里，重跑只是把同一份内容再写一遍，还得先 hydrate 六个榜，而且六个脚本会各建一个版本、互相继承六次
- 写量约等于六个榜的总行数（当前约 7.6 千行），建议一周点一次

数据内容不变 —— 想连同「还没发布的候选」一起发出去，先按上面的正常发布各点一次，再点全量。

**每阶段四项验收：**

```bash
V="SELECT val FROM app_config WHERE key='config.current_version'"

# 1. 当前版本各榜条数（与源文件条数逐榜核对）
pnpm d1 execute horizons-db --remote \
  --command="SELECT board, COUNT(*) n FROM board_listed WHERE version=($V) GROUP BY board"

# 2. 排名无空洞：MIN 必须是 1，MAX 必须等于 COUNT
pnpm d1 execute horizons-db --remote \
  --command="SELECT board, MIN(rank) mn, MAX(rank) mx, COUNT(*) n FROM board_listed WHERE version=($V) GROUP BY board HAVING mn<>1 OR mx<>n"
# 期望 0 行。有行说明排名有断层，不能发布

# 3. 构建产物与迁移前逐字节比对
pnpm build && git diff --stat apps/site/dist/

# 4. 抽查 3 个详情页
```

> 注意：`board_items.status` 只有 `candidate/enriched/rejected`，**没有 `listed`**。已发布数据一律查 `board_listed` 并带当前 version 条件。

**第 3 项是关键验收**：数据只换了存储位置，页面应该一个字都不变。若有 diff，说明序列化或字段顺序有问题，先修再继续。

## 11. 风险清单

### 11.1 D1 硬约束（会直接改变实现方式）

| 约束 | 影响 |
|---|---|
| 无交互式事务 | 发布靠"写新 version → 切指针"，不能靠回滚 |
| `batch` 才是原子的 | 每次发布 = 若干原子批，中途失败靠指针未切换来兜底 |
| 单行上限 1 MB | readme 等长文本必须外置 R2 |
| `SELECT *` 读整行 | detail 必须拆表，否则列表页慢一个数量级 |
| 写入放 Actions，不放 Worker | 1500 行写入需几十秒，Worker 会超时 |
| 免费计划 10 万行写/天 | 当前 2600 行/次，余量充足 |

### 11.2 最容易出错的三处

1. **allowlist 读失败的 fallback 方向**：必须落到"全锁"，绝不能落到"放行"
2. **会员页缓存头**：`full` + `public` = 全站泄露
3. **`ALLOW_PARTIAL` 开关忘了关**：迁移完成后必须恢复严格断言，否则数据缺失不会被发现

### 11.3 回滚能力

| 场景 | 操作 | 耗时 | 边界 |
|---|---|---|---|
| 单个榜数据异常 | `UPDATE app_config SET val='file' WHERE key='data_source.xxx'` | 秒级 | 文件还在时有效 |
| 整期发布有误 | `UPDATE app_config SET val='<上期version>' WHERE key='config.current_version'` | 秒级 | **仅最近 3 期内可回** |
| 名单查历史 | 查 `board_release_items` | 秒级 | **永久**，任何期都可查 |
| 库被写坏 | `wrangler d1 time-travel restore` 或导入 R2 备份 | 分钟级 | 取决于备份频率 |
| 彻底放弃 | 恢复 `content/*.json` 读取路径 + 删表 | 小时级 | 需文件未删 |

**两个必须记住的边界：**

1. **`board_release_items` 永久保留**，所以"上期第 37 名是谁"永远查得到 —— 即使数据版本已被清理
2. **详情数据只回溯 3 期**，第 4 期前的 `board_listed_details` 已被物理删除。这是 138 MB 换来秒级回滚的代价

**所以 `content/*.json` 在阶段 3 全部验收通过、观察两周之前，一个都不能删。**
